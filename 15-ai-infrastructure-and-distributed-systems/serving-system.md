# 从请求到 GPU：拆开一个模型服务

**中文** · [English](serving-system.en.md)

假设我们要部署一个生成式助手。模型权重已经有了，单条请求也能返回答案。接下来要解决的是：谁接收请求，谁决定等多久，谁分配缓存，机器出问题时怎样停止浪费计算，以及新模型怎样安全替换旧模型。

下面是教学系统，不是任何公司的内部架构。所有算例都注明假设，不代表某款 GPU 或框架的实测性能。

## 请求经过哪些层？ {#stack}

先看一次请求怎么走，再看哪些决策在后台发生。这里按职责分层，不要求每一步都独立部署。

<div class="system-flow" role="group" aria-label="模型服务的请求路径与部署控制">
<section class="system-flow-lane">
<h3>请求路径</h3>
<ol><li>客户端提交输入、截止时间和取消信号</li><li>入口检查鉴权、限额与接纳条件</li><li>路由选择可用副本</li><li>引擎排队，分配 KV，安排本轮计算</li><li>worker 执行模型与通信</li><li>token 逐步返回客户端</li></ol>
<p>截止时间和取消信号要传到引擎，不能只停在入口。</p>
</section>
<section class="system-flow-lane">
<h3>部署与容量控制</h3>
<ol><li>取得已验证的模型与配置</li><li>加载、预热并检查就绪状态</li><li>向路由登记可接流量的副本</li><li>根据队列与缓存指标决定扩缩容</li><li>旧副本停止接新请求，排空后退出</li></ol>
<p>引擎提供测量，控制层调整容量；新增资源不等于立刻可用。</p>
</section>
</div>

| 层 | 决定什么 | 需要传下去什么 | 该测什么 |
| --- | --- | --- | --- |
| 入口 | 请求是否有效，是否还有预算接收 | request ID、截止时间、身份范围、输入限制 | 拒绝率、输入长度、入口开销 |
| 副本路由 | 哪个可用副本接收请求 | 模型版本、缓存相关信息、剩余时间 | 各副本负载、路由等待、版本分布 |
| 引擎调度 | 本轮算哪些 token，KV 放在哪里 | 已算 token、采样状态、取消状态 | 排队时间、缓存占用、抢占和批次组成 |
| 计算进程 | 具体执行哪些算子与通信 | 张量、执行计划、并行组 | kernel 时间、带宽、通信等待和错误 |
| 部署控制 | 加载、预热、切流、排空、回滚 | 可用版本、健康状态、资源请求 | 就绪时间、发布失败、资源缺口 |

例如 [vLLM V1 架构](https://docs.vllm.ai/en/stable/design/arch_overview/)把 HTTP 与输入处理、engine core 的调度和 KV 管理、GPU worker 的模型执行分开。读源码时可以沿这几个职责找入口；进程布局和参数则应以实际部署版本为准。

vLLM 与 SGLang 的选择不宜简化成“一个负责吞吐，一个负责缓存”。先检查模型、硬件、并行方式、量化和集成要求，再用同一负载比较。具体机制与生态差别放在[框架对比](../06-systems/inference-frameworks.md)；换引擎不意味着入口限流、部署恢复和端到端评估就不需要了。

## 用户看到的慢，可能不是模型算得慢 {#timeline}

预填充（prefill）处理输入，解码（decode）继续生成。用户还会经历入口处理、排队和网络传输。考虑一个简化请求：

| 阶段 | 假设耗时 | 用户在等什么 |
| --- | --- | --- |
| 输入校验与准备 | 6 ms | 请求进入服务 |
| 排队 | 80 ms | 资源可用 |
| prefill 到首 token 就绪 | 60 ms | 输入计算与第一次采样 |
| 首 token 送到客户端 | 10 ms | 序列化和传输 |
| 后续每个 token 到达间隔 | 20 ms | 后续计算、调度与传输的合并结果 |

这里把第一次采样包含在 60 ms 中，因此首 token 延迟（time to first token，TTFT）为：

\[
T_{\rm first}=6+80+60+10=156\ \mathrm{ms}.
\]

若恰好输出 100 个 token，且后续到达间隔固定为 20 ms，完整输出耗时是：

\[
T_{\rm complete}=156+(100-1)\times20=2136\ \mathrm{ms}.
\]

只把 60 ms 的计算优化到 40 ms，首 token 会从 156 降到 136 ms，排队仍占很大一部分。反过来，吞吐更高但等待更久的批处理，也可能让用户觉得更慢。

这是单次请求的分解，**不能把每层的 p99 相加当成端到端 p99**。实际要记录整条请求，并按输入长度、输出长度、缓存命中和流量段比较。逐 token 到达间隔（inter-token latency，ITL）也要说明测在引擎还是客户端；两者受到的缓冲与传输影响不同。

## KV cache 为什么能决定接多少请求？ {#memory}

假设一个普通 GQA Transformer 有 32 层、8 个 KV head，每个 head 维度为 128，K 和 V 都用每元素 2 字节保存。先忽略分页浪费、共享前缀、滑动窗口和其他缓存压缩。每条序列每个已缓存 token 的 KV 大小是：

\[
b_{\rm token}=2\times32\times8\times128\times2
=131072\ \mathrm{bytes}=128\ \mathrm{KiB}.
\]

前面的 2 表示 K 和 V；最后的 2 是元素字节数。这里是**一份完整模型的逻辑 KV 总量**，不是任意并行配置下每个设备都占这么多。分片与复制会改变设备上的分布，MLA 等架构也不能直接套这个公式。

| 请求长度预算 | 每条序列的逻辑 KV | 32 条序列合计 |
| --- | --- | --- |
| 输入 2,048 + 输出上限 512 = 2,560 token | 320 MiB | 10 GiB |
| 输入 8,192 + 输出上限 512 = 8,704 token | 1,088 MiB | 34 GiB |

相同的“并发 32”，只改输入长度，缓存预算就差了 24 GiB。这里按输入加最大输出做保守预算；实际引擎可能逐步分配，不会一开始占满所有输出空间。但如果允许大家都生成到上限，就要有应对缓存耗尽的策略。

先从可用内存中扣掉权重、激活峰值、运行时和安全余量，剩下的才是 KV 预算。即使还有 10 GiB，也不能直接保证第一行放得下：表中没有计入分配粒度和暂存开销。**请求数限制和 token 预算不是同一个限制。**

前缀缓存（prefix caching）可以复用真正相同且兼容的前缀计算，不是把文本相似的两段话当成同一缓存。命中率还会随路由、驱逐和流量变化；容量评估至少分别测冷缓存和代表性命中率，不能只报最理想的热缓存结果。

## 副本、模型并行和分离部署解决不同问题 {#placement}

| 选择 | 主要想解决什么 | 新的成本与限制 |
| --- | --- | --- |
| 增加独立副本 | 总请求量超过单副本容量 | 重复权重、缓存分散，需要负载均衡 |
| 张量并行（tensor parallelism，TP） | 拆分模型计算与存储 | 每层通信，对互联敏感；一组 worker 共同服务 |
| 流水线并行（pipeline parallelism，PP） | 按层分配模型 | 阶段间传输、流水线气泡与调度复杂度 |
| prefill / decode 分离 | 减少阶段相互干扰，分别配置资源 | KV 传输、两边的容量配比、路由与恢复更复杂 |

一个 TP 组通常是一个逻辑副本，不是几个可以随便接独立请求的完整副本。组里一个 worker 失败，可能要停止或重建整组；切到另一副本也不代表 KV 状态会自动跟过去。

分离部署也要算传输账。[SGLang 的说明](https://docs.sglang.io/docs/advanced_features/pd_disaggregation)介绍了 prefill 干扰 decode 的问题。举个独立于框架的假设：需要传输 1 GiB KV，有效传输带宽为 8 GiB/s，那么仅载荷传输就需要 125 ms，还没算排队和协议开销。

如果原先只能减少 40 ms 干扰，并且这 125 ms 完全落在请求关键路径上，那么单请求延迟不会因此更好。能否通过重叠传输、提高整体容量或改善尾延迟获益，必须在目标负载下另测。不要把“架构更复杂”当成“必然更先进”。

缓存亲和路由也有类似取舍：把相同前缀尽量送回原副本能省计算，但热门前缀可能让一个副本排长队。比较的是**省下的计算和增加的等待**，不能只看命中率。

## 训练怎样接到这条服务链？ {#training}

模型更新不该发生在请求的关键路径里。一个最小的离线更新流程是：

<div class="system-flow" role="group" aria-label="训练结果如何成为可发布的服务版本">
<section class="system-flow-lane">
<h3>得到可恢复的训练结果</h3>
<ol><li>固定数据快照与转换版本</li><li>采样、分片，构建 batch</li><li>前向、反向、梯度同步与参数更新</li><li>保存可恢复的训练状态</li></ol>
<p>数据位置和优化器进度也属于恢复状态。</p>
</section>
<section class="system-flow-lane">
<h3>验证后再进入服务</h3>
<ol><li>做任务评估与回归检查</li><li>准备发布权重、tokenizer 与配置</li><li>加载、预热与小流量验证</li><li>通过后再扩大流量</li></ol>
<p>模型更新进入前面的部署路径，不阻塞正在执行的请求。</p>
</section>
</div>

DDP 通常复制模型并同步梯度；FSDP2 则分片训练状态，在计算前按组聚合所需参数，并通过相应通信处理梯度。选型要同时看显存与通信，不能只看单次前向速度。[PyTorch FSDP2 教程](https://docs.pytorch.org/tutorials/intermediate/FSDP_tutorial.html)给出了参数聚合、计算与预取的执行顺序；更完整的选择见[训练框架](../06-systems/training-frameworks.md)。

还有一种不显眼的错误：分布式程序没报错，目标却变了。假设两个 rank 分别有 2 和 6 个有效 token，局部平均 loss 分别是 1 和 3。若目标是所有有效 token 的平均 loss：

\[
\bar L=\frac{2\times1+6\times3}{2+6}=2.5,
\qquad \frac{1+3}{2}=2\ne\bar L.
\]

把局部平均直接再平均，会给短序列那边过高权重。这里展示的是目标值的算术；真正写反向时，还要核对框架的梯度归约、梯度累积和全局有效 token 数，不能简单把显示的 loss 改成 2.5 就算修好。

训练恢复也不只是加载权重。优化器、学习率进度、随机状态、数据游标和分片配置决定接下来做什么；推理发布则未必需要这些状态。两个产物可以共享权重，但用途与验证不同，详见[checkpoint 与恢复](../practice/post-training/checkpoint-and-resume.md)。

## 上线前怎样把链路走一遍？ {#checks}

| 检查 | 一个实际可做的动作 | 要观察的结果 |
| --- | --- | --- |
| 版本配套 | 同时核对权重、tokenizer、模板、采样配置和缓存隔离规则 | 新旧版本不误用彼此状态 |
| 就绪条件 | 在权重加载和预热未完成时发送测试流量 | 未就绪实例不接正常请求 |
| 请求取消 | 客户端中途断开 | 队列与引擎收到取消，关联资源最终释放 |
| 发布排空 | 停止给旧副本派新请求，再等待已有请求完成 | 不悄悄切断流式输出；超时有明确处理 |
| 失败恢复 | 模拟 worker 失败或依赖超时 | 重试有预算，错误有归属，不无限堆积 |

先用短、中、长输入，以及不同输出上限组成负载，再讨论框架快不快。固定短提示词的峰值吞吐无法回答长短请求混合后的用户体验；也不要把拒绝和超时请求从统计中消失。

下一篇[排队、容量与故障](queues-and-failures.md)会把这些边界变成可以手算和运行的小模型。全部例子是容量估算与排错练习，不是生产部署配置。
