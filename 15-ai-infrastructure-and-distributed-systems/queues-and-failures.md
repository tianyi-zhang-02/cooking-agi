# 排队、容量与故障：请求多了以后怎么办？

**中文** · [English](queues-and-failures.en.md)

服务开始变慢时，“再加几个副本”有时有用，有时来不及。更关键的是先看清：请求在哪里等，剩余时间还够不够，扩出的实例何时能接流量，以及失败后有没有把原来的一次请求变成更多工作。

下面用可复算的小模型讲这些问题。它们刻意简化了输入长度和批处理，不用于直接推算真实 GPU 集群规模。

## 先定义什么叫一次成功 {#slo}

只看成功请求的延迟会漏掉超时和拒绝。假设我们定义的服务质量指标（service level indicator，SLI）是：在统计窗口内，**合法且属于服务范围的请求中，按约定时限完整返回有效响应的比例**。其中因服务过载而拒绝的请求仍计为失败；格式不合法的请求另计。

目标（service level objective，SLO）设为 99.9%。若窗口内有 2,000,000 个符合统计条件的请求，允许失败的数量是：

\[
B=2{,}000{,}000\times(1-0.999)=2{,}000.
\]

这就是本例按请求数计算的错误预算（error budget）。若实际失败 3,000 次，成功率为 99.85%，比预算多了 1,000 次失败。它不能直接换算成停机多少分钟，因为流量随时间变化。[Google SRE 的 SLO 指南](https://sre.google/workbook/implementing-slos/)介绍了这种从用户可见结果定义指标和目标的方式。

“有效响应”也不等于“答案一定正确”。可用性、按时完成和模型质量可以分开追踪。返回空答案不能冒充成功；复杂任务的事实正确性则可能需要单独评估，不应假装 HTTP 200 就解决了。

## 为什么短暂的流量高峰会留下长队？ {#queue}

先看流体近似：假设每个请求耗费相同工作量，服务总处理能力固定为每秒 100 个请求，起初队列为空。流量以每秒 120 个请求持续 10 秒。

每秒多来 20 个，10 秒后积压：

\[
Q=(120-100)\times10=200.
\]

随后流量降到每秒 80 个，服务每秒只有 20 个名额可以消化积压，因此清空仍需：

\[
t_{\rm drain}=\frac{200}{100-80}=10\ \mathrm{s}.
\]

在 FIFO、速率恒定的近似下，排在这 200 个请求后面要先等约 \(200/100=2\) 秒。如果请求只剩一秒就到期，继续收进队列往往只是在延后报错。这个模型不包含批处理、长度差异和随机波动，更不能直接给出 p99，但能解释为什么“流量已经降下来了”不等于“用户不再排队”。

另一个有用的关系是 [Little 定律](https://www.mit.edu/course/other/urban_or_book/www/book/chapter4/4.4.html)：稳定系统中，平均在途请求数 \(L\)、有效流入速率 \(\lambda\) 与平均停留时间 \(W\) 满足：

\[
L=\lambda W.
\]

例如每秒 80 个请求，平均在系统里停留 0.25 秒，那么平均在途数是 20。这里的 20 包含正在等和正在处理的请求，**不是 GPU batch size**。三个量必须使用相同边界和统计口径；持续过载时，不能拿不稳定增长的队列套稳态均值。

## 扩容要留多少余量？ {#autoscale}

假设在固定的代表性请求分布下，一个副本满足延迟目标时可处理每秒 50 个请求。预计流量每秒 120 个，计划只用这份容量的 80%，所需副本数为：

\[
n=\left\lceil\frac{120}{0.8\times50}\right\rceil=3.
\]

80% 是本例人为选择的余量，不是通用最佳配置。三个副本总能力为每秒 150 个，但掉一个只剩 100，已经低于流量。若要求失去一个副本后仍满足同样的余量，需要准备四个同等副本，而且它们必须确实位于能隔离该故障的资源上。

这还没有算扩容等待。若新实例需要两分钟拉取权重和预热，十秒的突发已经结束，新增资源仍未就绪。要结合流量预测、预留容量、有界队列和接纳控制（admission control），而不是只盯一个自动扩容开关。

| 信号 | 能帮助判断什么 | 单看它可能误判什么 |
| --- | --- | --- |
| GPU 利用率 | 计算是否忙碌 | 高利用率不说明排队可接受；低利用率也可能在等通信 |
| 队列长度与最老请求年龄 | 是否开始积压、截止时间是否危险 | 不同长度请求的工作量不相同 |
| KV 占用与抢占 | 内存是否限制接纳和连续执行 | 不同架构、量化和前缀命中改变成本 |
| 完成率、TTFT 与 ITL | 实际输出与用户体验 | 只看已完成请求会漏掉超时和拒绝 |

[Kubernetes HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)可以依据资源或自定义指标调整副本，是一个周期性控制过程，不是瞬间增加可用容量。扩容单位也要匹配部署：模型并行的一组 worker 需要共同就绪，不能把其中一个进程当作完整服务副本。

## 重试为什么可能把小故障放大？ {#retry}

假设客户端、网关和下游调用都允许最多三次尝试（包括第一次）。最坏情况下，一次用户操作触发：

\[
3\times3\times3=27
\]

次最底层尝试。这是所有上层尝试都耗尽下层预算的上界，不是平均重试率。重试并不创造容量；服务因过载失败时，这些额外请求可能让恢复更慢。

要沿调用链分配一个总预算，而不是每层各自热心重试。退避和抖动（backoff and jitter）可以错开尝试，但仍要限制次数与总时间；剩余截止时间不够，就明确结束。过载处理与降级的更完整讨论见 [Google SRE](https://sre.google/sre-book/handling-overload/)。

流式生成还多一层麻烦：用户已经看到前半段，再启动一次生成可能得到另一份后半段。不要默默拼接。需要明确的恢复协议，或者告诉客户端这次请求中断了。涉及工具写入等副作用时，还要用适合业务的幂等机制，不能靠“请求 ID 相同”就假定下游不会重复执行。

## 故障时究竟保什么、放弃什么？ {#failure}

| 故障或压力 | 可以考虑的处理 | 不能悄悄破坏的条件 |
| --- | --- | --- |
| 请求已经无法按时完成 | 尽早拒绝或取消，释放后续资源 | 失败仍进入统计；客户端能分清可重试与不可重试 |
| 特征服务超时 | 用经过评估的缺失值或备用模型 | 不能绕过权限、资格与安全规则 |
| 一个并行 worker 失败 | 停止受影响组、重新建组或转移新请求 | 没有恢复协议就不能承诺无缝续接已有 KV |
| 新版本未预热完成 | 保留旧版本接流量 | 不能把进程存活当作可服务 |
| 热门前缀造成单副本拥塞 | 降低亲和性，把部分请求送去别处 | 记录缓存命中下降与等待减少，比较总效果 |
| 训练写 checkpoint 很慢 | 检查存储、频率与异步保存设计 | 异步写必须对应一致快照，未完成文件不能当可恢复点 |

降级（graceful degradation）也要有明确输出：小模型、较少候选和稍旧但仍允许使用的数据，各自会损失什么质量？在恢复正常以后，如何知道用户已经不再收到备用结果？把降级率和降级质量单独记录，别让它消失在总体成功率里。

## 用小程序检验方案 {#exercise}

从仓库根目录运行；站内测试需要 Python 3.11 或更新版本：

```bash
python3 15-ai-infrastructure-and-distributed-systems/code/capacity_checks.py
python3 -m unittest discover -s site/tests -p 'test_public_learning_routes.py'
```

它会复算 200 个积压、10 秒清空、3 个容量副本和额外 1 个容错副本，也会检查上一篇的 KV 与 token 加权平均例子。不连接外部服务，不产生云端费用。

可以自己改三次条件：

1. 恢复期流量仍为每秒 100 个。队列不会继续增长，也不会清空；计算不能假装给出有限恢复时间。
2. 输入从 2,048 增至 8,192 token。先重算 KV，再重新测单副本处理能力，不能保留原来的每秒 50 个请求假设。
3. 取消已经排队的请求。真实实现应让排队量和后续计算减少；这个流体模型没有取消事件，需要另外做带请求 ID 的离散事件测试。

最后把这些假设写回设计图：哪一层有队列，谁判断剩余时间，谁释放状态，谁能扩容。画清正常路径只是第一步；知道失败时如何收场，系统才算被拆开了。
