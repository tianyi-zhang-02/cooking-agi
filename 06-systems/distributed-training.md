# 多卡训练：数据、参数和计算，到底怎么分？

**中文** · [English](distributed-training.en.md)

> 最近审阅：2026-10 · 前置：[一次训练](../00-foundations/deep-dives/training-step.md)、[精度与显存](../00-foundations/deep-dives/precision-and-memory.md)

“用了多张卡”没有告诉我们模型怎样训练。**可能是多份模型各看不同数据，也可能一张卡只拿了模型的一部分；两者都会通信，但原因完全不同。**

先拿 4 层的小模型做示意。这里的尺寸和成本是教学假设，不是硬件 benchmark。

## 先分清两个需求

如果单卡能放下完整模型，只是训练太慢，可以考虑把数据分给更多卡。如果连模型状态都放不下，就要切分状态或计算；多复制几份模型不会解决显存不足（OOM）。

| 方式 | 主要分什么 | 每卡负责什么 |
| --- | --- | --- |
| 数据并行（Data Parallel）/ DDP | 数据 | 完整模型上的不同样本 |
| FSDP / ZeRO | 参数、梯度、优化器状态的全部或部分 | 保存分片，计算时按需要拼齐 |
| 张量并行（Tensor Parallel，TP） | 层内矩阵计算 | 一次矩阵运算的一部分 |
| 流水线并行（Pipeline Parallel，PP） | 模型层 | 一组连续层及经过它们的微批次（microbatch） |

它们可以组合。要解释一个配置，最好画出数据流、参数存放位置和通信发生时刻，而不只是说“三维并行”。

## DDP：各算一份梯度，再同步

各卡看不同样本，为什么还能保持同一份模型？先看梯度汇合在哪里：

```text
GPU 0：样本 A → 完整 4 层模型 → 梯度 g0 ┐
GPU 1：样本 B → 完整 4 层模型 → 梯度 g1 ├→ 平均梯度 → 各自更新
GPU 2：样本 C → 完整 4 层模型 → 梯度 g2 ┤
GPU 3：样本 D → 完整 4 层模型 → 梯度 g3 ┘
```

每个训练进程（用 rank 标识）都需要相同的初始参数、优化器状态和同步后梯度，副本才能保持一致。[PyTorch DDP](https://docs.pytorch.org/docs/stable/notes/ddp.html)会按梯度桶同步，并可与反向计算重叠；数据如何分片仍需要调用方安排。

DDP 是训练方式与框架接口，环形全归约（Ring AllReduce）是集合通信（collective）的一种实现算法，不是同一个层次的名字。单机多卡也可以用 DDP；具体通信算法由后端和配置决定。不要把“DP = 参数服务器、DDP = 多机环形通信”当作定义。

每卡 2 条样本，累积 4 次，4 个数据并行进程，每次更新对应 32 条样本；TP 组内的进程数不应再乘进这个样本数量。重复采样或采样器补齐也可能改变实际唯一样本数。

## 最容易漏掉的是全局分母

各卡先算平均损失，再把结果平均，就一定对吗？假设 rank 0 有 2 个有效 token，损失总和为 4；rank 1 有 6 个，损失总和为 6。先各自求均值再平均，得到 1.5；真正按 token 平均应是 1.25。区别在于：前者让两个进程各占一半权重，后者让每个有效 token 权重相同。

设一整个更新窗口的全局有效 token 数为 $T$，数据并行组的进程数（world size）为 $W$，rank 为 $r$ 的进程的可微损失总和为 $S_r$。若同步操作会对梯度取平均，可以在本地反向：

$$
\widetilde{\mathcal L}_r=\frac{W S_r}{T}.
$$

同步后梯度为

$$
\frac1W\sum_r\nabla\widetilde{\mathcal L}_r
=\frac{\sum_r\nabla S_r}{T}.
$$

有效数量本身不求梯度，需要先归并确定。若框架执行的是求和或另有归一化，系数相应调整，不能把这条公式不加判断地套上。

```python
loss_sums = [4.0, 6.0]
valid_counts = [2, 6]
world_size = len(loss_sums)
global_tokens = sum(valid_counts)
local_objectives = [world_size * total / global_tokens for total in loss_sums]
ddp_average = sum(local_objectives) / world_size
assert ddp_average == 1.25
assert sum(total / count for total, count in zip(loss_sums, valid_counts)) / world_size == 1.5
```

这段代码演示的是标量计算，梯度结论来自上面的线性求和。累积多个微批次时，分母要覆盖整个窗口；遇到全局零有效 token 要跳过或显式报错，不能除零。

## PS 与 Ring：梯度怎样到达更新的位置？

参数服务器（Parameter Server，PS）由工作进程（worker）推送梯度、服务器维护参数或参数分片；它可以同步，也可以异步，不能把 PS 直接等同于陈旧梯度（stale gradients）。同步全归约则让各参与者取得归约结果。两种组织方式都需要定义一次更新到底包含哪些样本。

环形全归约常用两个阶段：先归约分片（reduce-scatter），让每个进程拿到完整归约结果的一块；再收集并拼齐（all-gather），让所有进程拿齐各块。集合通信的定义与实现算法要分开：[NCCL 的介绍](https://developer.nvidia.com/blog/fast-multi-gpu-collectives-nccl/)可帮助理解环形通信，但这是历史文章，不是说今天所有通信都固定选择环形算法。

先算 4 卡归约 120 MB 梯度：等分后每块 30 MB，每个阶段发 3 轮，两个阶段合计每卡发送 180 MB，而不是把每张卡全部梯度都分别发送给其他 3 张卡的 360 MB。

推广到 $P$ 个进程、每卡 $S$ 字节的消息，假定均匀分块和理想环路：每轮发送 $S/P$，每阶段 $P-1$ 轮，所以**每卡发送量**为

$$V_{\text{send}}=2\frac{P-1}{P}S.$$

接收量也一样；若把发送和接收加总，需要再乘 2。

若每轮固定延迟为 $\alpha$、有效带宽为 $B$，串行轮次的简化成本为

$$t_{\text{ring}}\approx2(P-1)\alpha+2\frac{P-1}{P}\frac{S}{B}.$$

这里忽略归约计算、链路争用、分块重叠与实际拓扑。大消息可能受带宽限制，小消息可能受轮次延迟限制；这个公式不能替代性能分析工具（profiler）。一次全归约的耗时怎样估、怎样量出通信等待，见[性能：多卡通信与性能分析](../12-infra/performance.md#communication)。

```python
def ring_traffic(message_bytes, ranks):
    if type(ranks) is not int or ranks < 1 or type(message_bytes) is not int or message_bytes < 0:
        raise ValueError("expected positive integer ranks and nonnegative integer bytes")
    sent = 2 * (ranks - 1) * message_bytes / ranks
    return {"sent_per_rank": sent, "received_per_rank": sent, "rounds": 2 * (ranks - 1)}

assert ring_traffic(120_000_000, 4)["sent_per_rank"] == 180_000_000
assert ring_traffic(120_000_000, 1)["rounds"] == 0
```

### 异步不是只省掉等待

用 $L(w)=w^2/2$、学习率 0.5 算一次更新。初始 $w=2$，第一次更新后为 1。下一次若用当前梯度 1，就得到 0.5；若另一工作进程刚送来在旧参数 2 上算的梯度 2，就得到 0。这里使用旧梯度的更新碰巧更接近最优点，但不能据此说它更好——它已经不是同一条优化轨迹。

实际系统应记录梯度基于哪个参数版本、可接受多旧的更新、是否丢弃或重加权，以及恢复时怎么处理在途工作。只有梯度同步更快，不足以证明训练结果相同。

## FSDP / ZeRO：别让每卡都长期保存全部状态

分片究竟省掉哪些常驻状态？假设参数、梯度、优化器状态分别是 2、2、12 GB，4 卡情况下，仅看理想的常驻状态：

| 策略 | 每卡状态量 |
| --- | ---: |
| 全复制 | $2+2+12=16$ GB |
| ZeRO Stage 1：仅优化器分片 | $2+2+12/4=7$ GB |
| ZeRO Stage 2：优化器与梯度分片 | $2+2/4+12/4=5.5$ GB |
| ZeRO Stage 3：三者都分片 | $(2+2+12)/4=4$ GB |

这里没算激活、通信缓冲区和临时拼齐的参数。4 GB 不是训练峰值承诺，最大的计算单元也必须能放下。

[ZeRO](https://arxiv.org/abs/1910.02054)正是分阶段切分优化器状态、梯度和参数；[FSDP2](https://docs.pytorch.org/tutorials/intermediate/FSDP_tutorial.html)介绍了全分片训练的具体实现。它们并不是同一套 API，但可以放在“减少状态复制”这个问题下理解。

这些分片怎样参与计算？以全分片、计算后重新分片的一种路径为例：

```text
本卡持有参数分片
    → all-gather 当前模块需要的参数
    → forward / backward
    → reduce-scatter 梯度
    → 用本地 optimizer 状态更新本地分片
```

何时释放完整参数、反向前是否重新收集、是否提前预取（prefetch），都影响峰值和通信量。不能只拿总显存除以卡数。

### Stage 2 通信量相同，为什么不一定一样快？ {#zero-communication}

先看更新后的参数要去哪儿。Stage 2 里，每卡只更新自己负责的那部分参数；下一轮各卡还要跑完整模型，所以必须把更新后的分片重新拼齐。省掉完整梯度的长期存储，不等于省掉了所有同步。

用一个能手算的通信账：4 个进程，完整梯度与完整参数各为 8 MiB，按等分环形算法实现，只数**每个进程发出的 payload**，不把接收量再加一次。一次归约分片或收集拼齐各发送 $8\times3/4=6$ MiB：

| 一个更新周期的简化路径 | 每进程发送量 |
| --- | ---: |
| DP：梯度归约分片 → 拼齐梯度 | 6 + 6 = 12 MiB |
| Stage 2：梯度归约分片 → 更新本地分片 → 拼齐参数 | 6 + 6 = 12 MiB |
| Stage 3：前向拼齐参数 → 释放 → 反向再次拼齐 → 梯度归约分片 | 6 + 6 + 6 = 18 MiB |

这是对 [ZeRO §7](https://arxiv.org/html/1910.02054v3#S7)通信分析的具体化，假设参数和梯度传输精度相同、没有梯度累积或额外的参数收集。实际的分桶方式、参数保留和重算策略可能改变这条路径；Stage 3 的 18 MiB 不是所有配置的固定值。

字节相同，耗时仍可能不同：消息拆得多碎、何时发起、能不能与计算重叠，以及最慢的进程，都在影响等待时间。于是要同时看**发了多少、什么时候发、等了多久**，而不是只凭“通信量没增加”判断性能。这里没有跑多卡基准测试。

## TP：一次矩阵运算由几张卡合作

两张卡算出的局部结果，应该拼接还是相加？先算一遍完整的矩阵乘法：取 $X=[1,2]$，$W=\begin{bmatrix}1&3\\2&4\end{bmatrix}$，完整输出为 $[5,11]$。把权重矩阵按行切开，输入也按对应维度分开，两张卡分别算出 $[1,3]$ 和 $[4,8]$，相加恢复结果；不是平均。合并方式取决于切的是哪一维。

对行向量写法 $Y=XW$，可以按 W 的列切：

$$
\begin{aligned}
W&=[W_1\;W_2],\\
Y&=[XW_1\;XW_2].
\end{aligned}
$$

也可以沿输入维度切，得到需要相加的局部结果：

$$
\begin{aligned}
X&=[X_1\;X_2],\\
W&=\begin{bmatrix}W_1\\W_2\end{bmatrix},\\
Y&=X_1W_1+X_2W_2.
\end{aligned}
$$

[Megatron-LM](https://arxiv.org/abs/1909.08053)展示了怎样配合列切和行切组织 Transformer 层。是否要拼回完整的中间结果，取决于下一步需要什么；每层都拼齐，可能只是多传了一遍数据。

TP 的通信频率可能很高，通常更依赖高速互联（NVLink 与 NVSwitch 见 [GPU 架构](../12-infra/gpu-architecture.md)）。小矩阵切得太碎时，通信和调度开销可能超过收益。

如果想把这一步算透，读[张量并行：两张卡怎样算同一层？](tensor-parallel.md)。那里用一个两层 FFN 跟完前向与反向，区分拼接、求和与平均，再解释“一层 Decoder 四次通信”的适用条件。

## PP：分层之后，别让卡一直等着

把层 1–2 放在 GPU 0，层 3–4 放在 GPU 1。一个批次串着走时，GPU 1 一开始没活，GPU 0 做完前向又可能等待。把批次拆成多个微批次，可以让不同阶段同时处理不同数据。

理想的等耗时、无通信开销的 GPipe 式填充／排空（fill/drain）估算中，$P$ 个流水线阶段、$M$ 个微批次，利用率约为：

$$
\frac{M}{M+P-1}.
$$

2 个阶段、4 个微批次时为 80%。真实调度的流水线气泡（bubble）、前反向比例、负载不均和显存占用都会改变结果；更多微批次也不是无限免费。[GPipe](https://arxiv.org/abs/1811.06965)是理解这个过程的原始资料。

**调度顺序与参数更新时间是两件事。** 1F1B 说的是稳态下交替做前向与反向，不意味着每做完一个微批次就更新权重。同步训练仍可累积完整个批次再更新。[PyTorch 的流水线接口](https://docs.pytorch.org/docs/2.14/distributed.pipelining.html)支持多种调度；讨论 [PipeDream](https://arxiv.org/abs/1806.03377)的异步更新与权重版本暂存（weight stashing）时，要另外说明权重版本。

### PipeDream 为什么还要保存旧权重？

用两层标量模型 $y=bax$，令 $x=1,a=2,b=3,L=y^2/2$。前向得到 6，正确的 $\partial L/\partial a=6\times3=18$。若反向时直接使用已经改成 4 的 $b$，旧激活配上新权重就给出 24。这个例子说明为何版本重要，不是完整的 PipeDream 调度模拟。

在允许流水线更新的设计里，同一个微批次的前向和反向之间，参数可能已经改变。权重版本暂存保存该微批次前向使用的权重版本，让反向使用匹配的局部导数。[PipeDream](https://arxiv.org/abs/1806.03377)

保存旧版本会增加状态；而且局部前后向版本一致，不自动保证所有阶段使用同一个全局版本，更不使异步训练等同于大批次同步 SGD。对比实验要分别检查更新语义和吞吐，不只看气泡消失了多少。

## SP、CP、EP：名字接近，切的东西不一样

先问一个具体问题：把 8 个 token 分给两张卡，GPU 0 拿前 4 个，GPU 1 拿后 4 个，能否各算各的？若各自只在本卡算因果注意力，第 8 个 token 就看不到前 4 个，模型已经变了。CP 要解决的是保留这些依赖，同时分摊存储与计算，不是简单拼回输出。

| 方式 | 先看什么 | 不能省略什么 |
| --- | --- | --- |
| 序列并行（Sequence Parallel，SP） | 在 Megatron 的用法中，配合 TP 切 LayerNorm、dropout 等部分的序列激活 | 不能据此说注意力计算已沿序列切到多卡上（配合的 TP 切的是注意力头） |
| 上下文并行（Context Parallel，CP） | 沿序列切输入与激活，各卡拿一段上下文 | 本地 query 仍需要远处的 key/value，必须组织交换 |
| 专家并行（Expert Parallel，EP） | 将不同专家放到不同设备 | token 派发、结果归并与负载不均 |

这里采用 [Megatron 对 SP / CP 的区分](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/features/context_parallel.html)。别的框架可能把序列切分统称为 SP，读文档时要看实际的数据流。

EP 则是另一个问题：一个 token 选中两个专家，若专家在远端，就要发送激活，并把结果送回原位置后加权合并。[Megatron 的 MoE 并行说明](https://github.com/NVIDIA/Megatron-LM/blob/main/megatron/core/transformer/moe/README.md)展示了它怎样与其他并行方式组合。选中专家的比例不是通信字节比例，更不保证固定倍数加速；热点专家仍可能让别的卡等待。

## 推理部署时，卡怎么分？ {#eight-gpus}

训练里的并行方式，到了推理部署要换个问法：同样是八张 GPU，是八张合作跑一份模型（TP8），还是八份模型各接各的请求（DP8）？MoE 的专家怎样跨副本分布？PP 的 KV 存在哪张卡、相邻阶段每步传多少字节？这几笔账放在 [vLLM 与 SGLang：多张 GPU 的拼法](inference-frameworks.md#deployment-map)，和推理引擎的调度一起讲。

## Offload：把状态移出去，也要算回来要多久

例如每次更新顺序传出 2 GB 梯度、传回 2 GB 权重，两个方向的有效带宽都假设为 25 GB/s，仅传输就约需 `2/25 + 2/25 = 0.16` 秒，尚未计 CPU 更新。这里用十进制 GB；它不是任何显卡的实测参数。

这就是状态卸载（offload）需要同时算容量和时间的原因。CPU 内存能缓解显存压力，但不是免费扩容。优化器更新若移到 CPU，就要考虑梯度传出、更新后的参数传回，以及 CPU 自身的计算时间。小批次下，GPU 很快算完，反而可能一直等 CPU。[ZeRO-Offload](https://arxiv.org/abs/2101.06840)讨论的正是这些放置与调度取舍。

因此“理想状态量除以卡数”只能算一部分账。还需要明确临时拼齐的参数、激活、预取、链路带宽和优化器更新何时结束。参数更多、序列更长或卡更多，都可能改变原先的瓶颈。

想让通信与计算重叠来隐藏这段时间，还得有足够独立的计算，并且下一步不能早于所需权重到齐。真实关键路径取决于依赖、预取粒度、内存与争用，不能简单把所有时间都取一次 `max` 就当作最终延迟。

## 恢复训练：不只是重新读取参数

最容易验证的方案是在同步更新边界保存，先排空流水线，再写检查点（checkpoint）。对于下面几类状态，都要决定是恢复还是明确重置：

| 状态 | 漏掉后会发生什么 |
| --- | --- |
| 参数、优化器、学习率调度器（scheduler）、更新步数 | Adam 动量或学习率轨迹改变 |
| 随机数生成器（RNG）、采样器 / 数据游标 | 重复或跳过样本，随机增强改变 |
| 尚未完成的梯度累积与有效 token 数 | 恢复后分母和批次不一致 |
| 分片映射、参数版本、在途微批次 | 加载了不匹配的状态，或重复应用旧梯度 |

不是每个工程都支持任意时刻恢复。先从“保存后多走一步”和“重新加载后多走一步”对照开始，固定随机性，比对损失、梯度和更新后的参数。支持改卡数恢复时，还要单独验证重新分片；不能只凭文件能读开就宣布恢复正确。

## 先检查正确性，再追吞吐

用小模型、固定样本和禁用 dropout 的设置，比对单卡与多卡的一次更新：损失、有效 token 数、梯度、更新后权重。再加入不同长度、空样本、梯度累积和检查点恢复。

性能则分别记录有效 tokens/s、每卡峰值、通信时间和慢卡等待。GPU 使用率高不一定代表有用工作多，持续显存不足后的重试或大量填充也不是有效吞吐。

选法可以很朴素：模型放得下先做 DDP 基线；状态放不下再考虑分片；单层计算过大看 TP；按层拆分看 PP。每加一种并行，都应能说清省下什么，以及新引入了哪次通信。

想沿代码检查这三种基本切法，可读 [Stanford CS336 `lecture_07.py`](https://github.com/stanford-cs336/lectures/blob/main/lecture_07.py) 中的 `data_parallelism_main`、`tensor_parallelism_main` 和 `pipeline_parallelism_main`：重点追踪数据切片、梯度归约和阶段间传输。后两者只演示前向，反向留作练习，也未覆盖通信与计算重叠；它们适合帮助理解数据流，不是完整的生产训练器。改成自己的多步训练练习时，也要检查何时清空梯度，避免无意中跨步累积。
