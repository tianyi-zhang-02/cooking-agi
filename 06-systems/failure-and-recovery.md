# AI 任务的失败与恢复：超时以后，到底做成了吗？

**中文** · [English](failure-and-recovery.en.md)

> 最近审阅：2026-11-02 · 文中流程和数字用于讲解，不是可直接部署的实现

用户让客服助手退一笔款。工具调用一直转圈，最后超时。最容易写出来的处理是“失败了，再试一次”，但退款可能已经成功，只是响应没回来。再退一次，错误就从“用户不知道结果”变成了“系统执行了两遍”。

这一篇接着[系统总览](README.md)讲模型外面的控制逻辑：怎么表示未知结果，哪里能重试，什么时候该停，以及用户回来以后怎样接着处理。无需先学某个 Agent 框架。

## 先分清任务、请求和外部动作 {#three-lifetimes}

| 对象 | 退款例子 | 生命周期 |
| --- | --- | --- |
| 用户任务 | 把订单 R17 的款退回去 | 可能跨多个页面访问，直到完成或明确停止 |
| 一次请求 | 浏览器等服务器回复 | 断网、超时或关闭页面就可能结束 |
| 外部动作 | 支付系统执行退款 | 不一定随着浏览器断开而停止 |

所以 HTTP 连接结束，不代表业务任务结束；文字生成停止，也不等于退款撤销。持久化的任务记录至少要能找到原动作、当前已知结果和下一步处理方式，不能只依赖聊天记录里的一句“处理中”。记录怎么关联到调用轨迹，见[任务与尝试次数](agent-observability.md#task-and-attempt)。

## 结果未知，要单独存下来 {#unknown-outcome}

下面是一个简化状态流程。权限、动作版本和业务规则由可信执行层检查，模型只提出请求。

<figure class="worked-update worked-update--pairs" id="recovery-flow" lang="zh-CN">
<figcaption>退款请求超时，不立即重新退款</figcaption>
<ol>
<li><strong>1 · 提交前检查</strong><span>确认目标、金额、权限和有效批准，保存这次动作的标识与参数版本。</span></li>
<li><strong>2 · 提交，等待结果</strong><span>提交到外部服务。收到可核实的成功结果，才标记已完成；确定未执行的拒绝则按原因处理。</span></li>
<li><strong>3 · 响应丢失，标记未知</strong><span>保留原动作，不换一个新标识重新提交。界面说明正在核对，不显示“退款失败”。</span></li>
<li><strong>4 · 核对，再决定</strong><span>读回原动作状态；或在接口明确支持时，用原幂等键与相同参数重试。仍无法确定就保持待核对，告警或交给有权限的人处理。</span></li>
</ol>
</figure>

幂等性（idempotency）说的是重复请求在规定范围内不重复产生同一个效果，不是“请求只发送一次”。唯一 `operation_id` 只有在服务端确实用它去重时才有这种作用。[AWS 的幂等 API 文章](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)专门讨论了重复请求和相同标识下意图变化的问题。

还要核对作用范围、有效期、参数比较以及失败响应的处理。例如 [Stripe API v1](https://docs.stripe.com/api/idempotent_requests)会复用已保存的响应，包括某些 500 结果；键被清理以后再用，就可能成为新请求。不能由此推断所有 API 都相同，也不能把“一直重试同一个键”当作必然恢复成功。

## 失败原因不同，下一步也不同 {#failure-policy}

| 看到的情况 | 可以考虑的处理 | 不该直接做什么 |
| --- | --- | --- |
| 查询接口短暂不可用 | 在总时间和次数预算内重试 | 无限重试 |
| 供应方限流 | 按接口约定退避，控制并发 | 立刻并行发更多请求 |
| 参数缺失或权限不足 | 修正输入，或走授权流程 | 原参数重复请求，期待下次碰巧成功 |
| 写操作超时，结果未知 | 查原动作或使用核实过的幂等机制 | 换新键再写一次 |
| 用户改变了金额或收件人 | 生成新动作版本，重新校验和确认 | 复用旧批准 |
| 回复生成中断，但订单已完成 | 保留订单结果，允许重新查看或生成说明 | 为了重写一句话，再执行订单 |

从“知道要退 20 元”到“真的退了 20 元”之间有执行边界。结构化输出合法、模型高把握、用户点过一次按钮，都不能单独证明动作已正确完成。

## 重试也要共用预算 {#retry-budget}

假设应用、工具封装和 HTTP 客户端三层都最多尝试 3 次，包含第一次。若最底层持续失败且每层都把次数用完，一次用户操作最多会触发 `3 × 3 × 3 = 27` 次底层调用，而不是 3 次。这是人为设定的上界，不是任何 SDK 的默认行为。

要先弄清 SDK 是否已经重试，再决定哪层负责。总截止时间（deadline）沿调用传下去，还要有总次数、token 和费用预算；次数没到，不代表时间一定还够。

例如一个只读查询的预算为 5 秒：

| 阶段 | 耗时 |
| --- | ---: |
| 入口与准备 | 0.2 s |
| 第一次调用超时 | 1.5 s |
| 本次退避等待 | 0.3 s |
| 第二次调用 | 1.5 s |
| 整理并返回结果 | 1.0 s |

合计 4.5 秒，只剩 0.5 秒，不够再按原配置完整尝试一轮。这里只演示预算，真实网络和排队还会占时间；显示部分结果、缩小任务或结束等待，各自需要产品约定，不能悄悄换个答案装作完成。

[AWS 的 timeout / retry 说明](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)强调退避和随机抖动（jitter）对减轻集中重试的作用。它们能错开请求，但不能让过载服务凭空多出处理能力；流量超过容量时还需要限流和拒绝新任务。

## 用户点了停止，到底停了什么？ {#cancellation}

不要用一个“已取消”覆盖所有阶段。界面可以简单，后台状态不能含糊：

| 点停止时的阶段 | 可以向用户说明什么 | 后台仍需做什么 |
| --- | --- | --- |
| 只在生成草稿，尚未提交写操作 | 已停止生成，草稿可保留 | 传播取消信号，释放能释放的计算资源 |
| 外部动作已提交，但结果未返回 | 已停止后续步骤，正在核对已提交操作 | 查询结果，不承诺动作没发生 |
| 已核实发送或退款完成 | 操作已完成；若支持，可另行申请撤回 | 执行单独的补偿流程，重新检查权限和条件 |

取消信号还可能和提交动作同时到达。应由服务端原子地决定该动作是否仍可提交；前端停止动画不解决这个竞争。对已经提交的动作，外部服务的取消接口也可能是尽力而为，需要读回最终结果。

补偿（compensation）不是让时间倒流。邮件可能已被读到，退订可能有手续费，另一笔业务也可能已经依赖原结果。[Azure 的补偿事务说明](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)讨论了这类限制：补偿依赖业务规则，本身也可能失败，应保留进度并允许人工处理。

## 失败时，备用方案能不能完成同一件事？ {#fallback}

生成服务不可用时，可以返回检索到的原文链接；但应明确没有完成总结。订单查询失败时，旧缓存也许能展示“截至某时刻的记录”，却不能冒充当前退款资格。备用模型则要重新检查工具能力、输出格式、数据去向和评估结果，不能只因 API 长得一样就认为可以互换。

有些能力能降级，有些条件不能：可以少生成几段解释，不能跳过授权；可以暂停写操作，不能拿猜测的执行结果填空。记录用了哪种备用路径，评估时单独看它的成功率和代价。

## 用故障注入检查，而不只测顺利的一次 {#failure-tests}

在沙箱里固定工具返回，分别把失败放在动作前后：

| 注入的情况 | 应检查的结果 |
| --- | --- |
| 提交前就失败 | 没有外部写入，任务可按规则重新开始 |
| 服务已执行，但响应丢失 | 核对后识别已完成，同一动作不重复写入 |
| 用户双击批准，或两个 worker 同时恢复 | 至多一个有效执行路径；界面收到同一业务结果 |
| 批准后参数发生变化 | 旧批准不能执行新动作 |
| 等待中刷新页面 | 读回任务状态，不靠重新提交恢复界面 |
| 提交后收到取消 | 不再发起后续动作；已提交部分继续核对结果 |

这些是测试要求，不是仅凭流程图就实现的保证。还要测试进程在“写入成功、保存本地状态之前”崩溃等边界；没有外部幂等或可核对结果的接口，不能轻易承诺端到端恰好一次（exactly-once）。
