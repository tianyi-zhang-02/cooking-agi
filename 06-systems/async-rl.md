# 异步 RL 与 AReaL：少等一会儿，数据会旧多少？

**中文** · [English](async-rl.en.md)

同一批任务里，有的回答五秒就能完成，有的要花一分钟调用工具。如果必须等整批生成结束才能训练，先完成的回答就只能等着最慢的任务。负责训练的 GPU 也可能因此空闲。

异步 RL 尝试让生成和训练同时推进：采样端继续收集回答，训练端拿到满足要求的一批数据就更新参数。例如，已收齐回答的组可以先用于训练，其他组继续生成。但如果训练目标依赖同一道题的完整组，仍要等组内成员到齐。不必等整批生成结束，并不意味着可以少用目标所需的数据。

重叠执行也带来一个问题：**训练已经向前走了几步，刚收到的回答可能还是旧模型生成的。** 这种新旧差距称为策略滞后。要判断异步是否有用，需要一起看省下了多少等待、留下了哪些可用数据，以及最终学得怎么样。

先读[一次 RL 更新](rl-systems.md)，再问两个问题：**减少了哪一道等待？训练使用的数据又由谁生成？**

下面用假设的版本记录和队列数字分析这些问题，没有运行异步训练或复现论文的加速比。资料核对日期：2026-10-30。[异步策略学习](../05-post-training/async-policy-learning.md)另讲 SAO；它和这里讨论的 AReaL 不采用同一个目标函数，不能直接互套。

## 哪些工作在同时进行？四种异步要分清 {#levels}

| 说法 | 可能重叠的工作 | 不自动意味着什么 |
| --- | --- | --- |
| HTTP / API 异步请求 | 客户端等结果时处理其他请求 | 训练已与采样并行 |
| 引擎异步调度 / 重叠调度 | CPU 安排下一轮，GPU 执行当前轮 | 正在更新模型参数 |
| 并发采样 / 环境交互 | 同时处理多个提示词，或同时运行多个工具、环境 | 允许训练消费旧版本样本 |
| 采样与训练重叠 | 生成与参数更新同时推进 | 没有策略滞后，或更新目标保持不变 |

所以，看到 `async_engine=true`，还不能断定整个 RL 训练循环都是异步的。还要看实际时间线上哪些工作同时进行、权重何时发布，以及数据何时进入训练。

比如，客户端同时发出四个请求、异步接收结果，最后仍等四条全部返回才训练，训练期间也不再生成。这已经有并发请求，却还没有采样与训练的重叠。下文关注的是最后一行：训练端更新参数时，其他采样与交互任务仍在推进。

## 沿时间线看数据落后了几个版本 {#trace}

### 先跟踪一条慢任务

把每次发布的策略记成 v10、v11、v12。任务 A 启动时用的是 v10；它还在生成，训练端已经通过其他数据更新到 v12。A 完成时，回答本身未必有错，但它反映的是 v10 的选择，不是 v12 的选择。

下面约定，训练端的 v12 指当前用于计算损失的参数版本，年龄定义为 $a=v_{\rm learner}-v_{\rm behavior}$。这只是本文为便于讲解采用的记号，并非所有框架都这样编号。再假设一组时刻：其他符合要求的数据已经足够支持两次更新与权重同步，分别在第 20、45 秒完成；第 45–65 秒，训练端保持 v12。这些时刻只用于推演，不代表任何框架的实际耗时。

| 事件 | 当前训练端版本 | 生成端 | 队列 / 训练决策 |
| --- | --- | --- | --- |
| 第 0 秒：开始 | v10 | 用 v10 启动长任务 A | A 尚未完成 |
| 第 20 秒：使用其他合格数据，更新并完成权重同步 | v11 | 新任务 B 用 v11，A 如何继续取决于协议 | B 的 behavior=v11 |
| 第 45 秒：又完成一次更新与权重同步 | v12 | 新任务 C 用 v12 | A、B 仍在运行 |
| 第 60 秒：A 完成，采用示例中的年龄上限 1 | v12 | A 交付 behavior=v10 的回答 | 年龄 2，A 不可用 |
| 第 65 秒：B 完成，仍采用上限 1 | v12 | B 交付 behavior=v11 的回答 | 年龄 1，可进入其他资格检查 |

这里假设 A 从头到尾使用 v10，B 从头到尾使用 v11；两次权重同步都只在各自的发布范围内生效。要让表中的过程成立，系统需要让旧版本继续服务这些任务，同时让其他任务使用新版本。另一种做法是等 A 结束，再替换它所在工作进程的权重。但如果所有工作进程都必须等 A 结束，就无法按表中的安排重叠执行。

表里的 A 运行了 60 秒，策略年龄却是 2；B 运行了 45 秒，年龄是 1。经过的秒数反映实际等了多久，版本差则反映训练端向前走了几步。若训练端一直没有更新，一条运行很久的任务也可以保持年龄 0。

也可以暂停 A，换成新权重后接着生成。这就是下文讨论的 partial rollout：一条回答的前后部分来自不同版本，不能再只标一个 v10。

### 版本没超限，不等于已经通过全部检查

即便 B 在第 65 秒通过年龄检查，只要它所在组还缺一个回答，就不能按要求完整组的目标立即训练。训练入口还要检查任务是否完成、组是否完整、掩码是否正确，以及是否重复投递；奖励和数据消费规则也必须符合要求。另外，版本差这个整数不能完全说明策略分布变了多少：一次大更新，可能比多次小更新带来的变化更大。

## 队列既决定吞吐，也决定数据来源 {#queue}

### 生成更快以后，数据可能只是在排更长的队

设生成端每秒交付 50 个训练单位，训练端每秒消费 40 个。为了便于手算，假设速度稳定、不限流，也不丢弃数据：

| 要算什么 | 计算 | 含义 |
| --- | --- | --- |
| 一分钟新增积压 | `(50 - 40) × 60 = 600` | 队列每分钟多出 600 个单位 |
| 前面有 400 个单位时的等待 | `400 / 40 = 10` 秒 | 只算排队，不含自己的训练时间 |

这里可以把完整组作为一个单位，但整次计算必须统一单位：每秒产出多少组，不能直接减去每秒处理多少 token。第二行还假设按先来先服务的顺序处理，没有其他优先级任务插队。

排队还会增加策略年龄。假设一份 v10 数据入队时，训练端为 v11；在等待的这 10 秒里，训练端恰好又完成两次版本更新。那么，使用这份数据时，训练端已经是 v13，数据年龄也从 1 变成了 3。若示例中的年龄上限仍为 1，只在入队时筛选就会漏掉这个变化，需要按训练目标要求，在消费时点重新判定。这里的“两次更新”是额外假设，不能由等待了 10 秒本身推出来。

此时继续增加生成并发，不一定能提高训练速度。下游处理不过来，可以用背压暂缓上游生产，也可以调整资源分配，或按明确规则丢弃数据。队列容量管的是能存多少，年龄上限管的是数据能落后多少，超时管的是任务或等待能持续多久。加大缓冲区只能容纳更多积压，不能让训练端每秒消费超过 40 个单位。序列长度、工具时延和模型学习过程也会影响产出速度，所以还需要按长度分组观察吞吐，并记录样本年龄分布。

### 丢掉慢任务，也改变了训练数据

若长任务更容易过期，留下的数据会偏向快任务。例如同题四个回答中，两个短回答先结束，两个长回答还在调用工具；只拿前两个训练，相当于让完成速度参与了样本选择。

沿用[上一篇的四个回答](rl-systems.md#exercise)：R1、R3 在第 5、6 秒先完成，奖励都为 1；R2、R4 分别在第 20、60 秒完成，奖励都为 0。完整组的奖励为 `[1,0,1,0]`，只减均值时，R1、R3 的优势值各为 0.5。若在第 6 秒把先返回的两条另当一组，均值变为 1，两条的中心化结果都为 0。提前开训不仅改变了开始时间，也改变了这个算例中的学习信号。

重要性比值处理的是不同策略对动作赋予不同概率的问题，并不会自动消除“只选先完成任务”带来的偏差。对 GRPO，如果优势估计依赖同一道题的一组回答，还必须避免把先完成的样本直接当成完整组。

## 生成策略、冻结快照和当前策略要分清 {#objective}

### 先算同一个 token 的概率

假设在完全相同的上下文里，生成策略赋予某个 token 的概率是 0.2，训练端当前模型赋予它的概率是 0.3。当前概率与生成概率的比值是 `0.3 / 0.2 = 1.5`。

如果没有保留生成时的概率，而是拿另一份旧检查点重算，得到 0.25，再把它代入分母，就会算成 `0.3 / 0.25 = 1.2`。这个 1.2 比较的是另一对分布，不是当前策略与真正生成这条数据的策略之间的比值。

比值 1.5 只说明当前策略赋予这个动作的概率更高，并不说明它值得鼓励。还要结合优势值与具体目标，才能决定这一项怎样影响更新。这里需要分清两件事：奖励与基准提供学习方向，概率比则用来处理产生数据的策略与训练策略之间的差异。

读公式或代码时，可以按下面的含义区分三个名称：

| 名称 | 本文中的含义 |
| --- | --- |
| behavior | 实际产生这个动作的行为策略，包括需要说明的采样设置 |
| old | 为某个训练目标保留的冻结策略快照，未必等于 behavior |
| current | 当前正在优化的策略 |

这里的 old 也不等于 RLHF 中用于 KL 约束的参考模型。名字都带“旧”或“参考”，用途却不同。训练时重新计算对数概率（logprob）可以是算法的正常步骤，但这并不等于找回了丢失的生成记录。

<details markdown="1">
<summary>展开：用公式看这两个概率比怎样连接</summary>

用 $\mu$ 表示真正产生动作的行为分布，$\pi_{\rm old}$ 表示冻结的训练策略快照，$\pi_\theta$ 表示当前策略。在同一上下文且分母非零时，有代数恒等式：

$$
\frac{\pi_\theta(a\mid h)}{\mu(a\mid h)}
=\frac{\pi_\theta(a\mid h)}{\pi_{\rm old}(a\mid h)}
\frac{\pi_{\rm old}(a\mid h)}{\mu(a\mid h)}.
$$

右边第一项比较 current 与 old，第二项比较 old 与 behavior；两项相乘，才还原为 current 与 behavior 的比值。

代入前面的数字，第一项是 `0.3 / 0.25 = 1.2`，第二项是 `0.25 / 0.2 = 1.25`，乘起来为 `1.2 × 1.25 = 1.5`。若只作算术演示，把每个比值各自截到 `[0.8,1.2]`，相乘会得到 1.44；先乘成 1.5 再截到同一区间，结果却是 1.2。这只是两种裁剪顺序的对比，还没有构成 PPO 的完整代理目标。

这**还不是完整的解耦 PPO 损失函数**。实际实现还要规定代理目标和优势值，明确哪些量停止梯度传播、怎样裁剪，以及如何在 token 或序列层面聚合、加权。分别裁剪两个比值，通常不等于先相乘再裁剪。PPO 原有的裁剪机制不能保证任意旧数据都可以安全使用。

</details>

### 同版权重也未必产生同一采样分布

假设词表只有三个 token，模型概率为 `[0.5,0.3,0.2]`。只保留概率最高的两个 token（top-2）并重新归一化，实际采样概率就是 `[0.625,0.375,0]`。若采到第二个 token，即使权重完全没变，原始模型概率与行为概率的比值也是 `0.3 / 0.375 = 0.8`，而不是 1。第三个 token 原本概率非零，此时却不可能被采到。

温度、top-p、量化与不同计算内核也可能影响概率。记录对数概率时，要说明它对应的是原始 logits 所定义的分布，还是经过采样变换后的分布。只存一个权重版本号，无法区分上面这两组概率。

如果采样把部分动作的概率截成零，而目标分布仍给这些动作非零概率，就不能仅靠采到的动作做通常的无偏重要性校正。问题在于采样分布的支持集没有覆盖目标分布，而不是样本太旧；调小队列的年龄上限也解决不了。

## AReaL 怎样处理旧数据，其他框架的上限又指什么 {#frameworks}

AReaL 将生成和训练分开运行，让二者可以重叠。它既要控制数据能落后多少，也要定义训练怎样使用这些数据。原始[系统论文（2025 年首次公开）](https://arxiv.org/abs/2505.24298)同时讨论了系统调度与目标函数调整。前面的例子说明了为什么两者要一起读：异步调用让任务继续推进，年龄控制决定哪些数据留下，训练目标则决定这些数据怎样参与更新。

## 一条回答中途换权重，要补记什么、重算什么 {#partial-rollout}

### 保留前半段，不等于它也变成了新模型生成的

假设前 20 个回答 token 来自 v10。系统暂停生成、切换权重，再用 v11 接着生成 30 个。这样不用把前 20 个 token 丢掉从头再来，但整条回答已经混合了两份策略：

| 回答位置 | 实际生成版本 | 需要保留 |
| --- | --- | --- |
| 第 1–20 个 token | v10 | 这些位置生成时的对数概率与动作标记 |
| 第 21–50 个 token | v11 | 新版本下的对数概率，以及从哪里恢复 |

仅记录 `behavior_version=v11` 会抹掉前半段的来源。应保留与每个 token 对齐的行为策略对数概率，以及版本边界或能起到同样追溯作用的信息。若中间夹了工具输出，那些位置是环境提供的内容，不能直接当成模型选出的动作。

例如，训练端已是 v12，前 20 个 token 的版本年龄为 2，后 30 个为 1。统一写成“整条年龄 1”，就会隐藏前半段的滞后。是否接收整条轨迹、如何处理分段，以及怎样计算优势值和损失，都需要由所选算法定义，不能只凭最后一次恢复时的版本号决定。

### 换权重后，旧 KV 怎么办

旧 KV 是用旧权重对前缀计算出的状态。保留那 20 个 token 的文字，不表示可以继续使用它们在 v10 下算出的 KV。换成 v11 恢复生成时，需要按实现重算前缀状态或使旧缓存失效；这也有计算成本。

重算前缀时，v11 读取的是已经确定的那 20 个 token，用它们建立后续生成需要的状态。它没有重新选择前 20 个动作，也没有把这些动作当时的行为策略对数概率改写成 v11 的概率。因此，重建缓存和保留行为记录是两件事，需要分别处理。

暂停、传权重、恢复只是控制步骤，还要检查内容、位置、掩码与版本是否对齐。中途换权重后接着生成，可以减少等待和重复生成，但不会把这 50 个 token 变回由同一策略生成的数据。

## 更快要用什么证据衡量 {#evaluation}

### 同时看速度、可用数据和学习效果

| 对照维度 | 至少同时记录 |
| --- | --- |
| 系统效率 | 固定 GPU 总数下的拓扑、各阶段资源分配、总时长与 GPU 小时数 |
| 有效数据 | 完成率、超时率、丢弃率、组完整率，以及长度与年龄分布 |
| 学习变化 | 更新次数、损失 / 概率比 / 裁剪指标、固定评估集与达到目标质量所需时间 |
| 一致性与恢复 | 行为策略记录、权重同步确认、KV 处理、重复消费与检查点 |

先看一组不涉及模型效果的假设数字：GPU 预算相同，都统计一分钟，组的定义也相同。方案甲生成 100 组，其中 90 组完整且未过期；方案乙生成 120 组，却只有 72 组符合要求。再假设训练端能消费全部合格组，那么原始产出虽然提高了 20%，可用于训练的组数反而从 90 降到了 72。即使合格组数也增加了，仍要用固定评估衡量学习效果：更新次数更多或奖励曲线更高，都不能单独说明达到同一目标质量所需的时间更短。

### 一个理想上限，为什么不能直接当实测加速

用 $T_R$ 表示生成一批可训练数据所需的时间，$T_L$ 表示用这样一批数据训练所需的时间。假设各阶段的资源分配已经确定、各批次耗时稳定，并忽略流水线启动时的填充、收尾时的排空，以及通信开销。此时，理想流水线的批次完成间隔由较慢的阶段决定，约为 $\max(T_R,T_L)$；串行执行则为 $T_R+T_L$。

假设两项分别是 60 秒和 25 秒，串行处理一批需要 85 秒。如果两阶段使用各自的资源重叠执行，第一批仍要走完两阶段，但进入稳态后可以约每 60 秒完成一批，理想吞吐是串行的约 `85 / 60 = 1.42` 倍。

沿用这组假设，展开三批数据的时间线。表中每格依次写“生成区间 → 训练区间”，时间单位为秒；各阶段的资源分配保持不变，仍忽略通信与发布开销。

| 批次 | 串行 | 生成与训练重叠 |
| --- | --- | --- |
| 第 1 批 | 0–60 → 60–85 | 0–60 → 60–85 |
| 第 2 批 | 85–145 → 145–170 | 60–120 → 120–145 |
| 第 3 批 | 170–230 → 230–255 | 120–180 → 180–205 |

两种安排下，第一批都在第 85 秒完成。重叠不会缩短它走完两阶段的时间，只会把后续批次的完成间隔从 85 秒缩短到 60 秒。只处理这三批时，总时长之比是 `255 / 205 ≈ 1.24`，还没有达到稳态的 1.42。对短任务，尤其不能忽略流水线填充和排空的时间。

这条时间线能否成立，还取决于数据是否符合训练要求。假设初始为 v10，每批训练结束后发布下一版，并让每批生成始终使用启动时的版本。重叠方案的第 2 批在第 60 秒已经用 v10 开始生成，第 85 秒发布 v11 时仍未结束；第 120 秒用它训练时，训练端已是 v11。因此，这种安排要求算法允许使用这份旧版本数据，也要求系统保留生成所需的旧版本。若坚持每批都必须等上一批更新后再采样，就又成了必须串行执行的依赖关系。

这个比较没有增加 GPU。若原先两阶段轮流占用全部卡，现在把同一批卡分给两个阶段，就需要重新测量耗时，不能继续套用 60 秒和 25 秒。每秒输出的 token 更多，也可能同时出现可用样本减少或评估质量下降。最终仍要比较达到相同目标质量所用的时间与资源。

第一轮练习可以先复算版本表、600 个单位的积压和概率比值。在三批时间线上标出每批的生成策略版本与训练时版本，再写出暂停 / 恢复和重复投递的状态机。第二轮再用小模型对照同步与限制策略滞后的异步运行。没有做过的收敛、长任务或故障实验，就保留为计划。这样才能具体回答：省下了哪段等待，多用了哪些旧数据，是否更早达到同一个学习目标。
