# 现代 AI 系统：模型只是其中一部分

**中文** · [English](README.en.md)

## 先看看模型前后还有什么

一个 AI 系统的结果，不只取决于模型。读到的数据、取出的记忆、找到的资料和调用的工具，都会影响它最后做什么。要改进系统，就得一起看这些环节，而不是只换一个更大的模型。

## 一次请求真正经过哪些环节

假设旅行 Agent 给用户订错了机票日期。

“模型答错了”只是最表面的描述。真正原因可能是：

- 用户在前一轮修改了日期，但状态没有更新；
- 搜索找到了过期的航班信息；
- 工具参数里的时区转换错误；
- 模型选对了日期，但执行层传错字段；
- 最终评估只检查回复文字，没有核对真实订单。

如果只盯着最后一句回答，很可能修错地方。

### 1. 用户目标：到底想解决什么

先说清楚任务、目标人群、失败成本和不能违反的条件。否则系统很容易优化一个方便测量、却不代表真实价值的指标。

### 2. 数据与反馈：模型看见的过去

数据由旧模型、产品界面和用户行为共同产生。它不是中立事实。详见 [数据与反馈](../01-data-and-feedback/)。

### 3. 表征与记忆：哪些信息要留下来

这一层决定本轮要用什么信息、哪些要留到以后的对话，以及新信息来了怎么更新旧记录。详见[表征与记忆](../02-memory/)。

### 4. 搜索与工具：怎样获取信息、执行操作

搜索负责找资料，工具负责查询或执行操作。接口没有报错，不代表信息就正确：搜到的文档可能过期，工具也可能读到了旧状态。

### 5. 模型与策略：系统怎样决定下一步

模型把目标、状态和证据组合起来，决定回答、追问、搜索还是行动。Post-training 则塑造这种行为倾向。

### 6. 运行与执行：能不能把事情做成

延迟、缓存、并发、重试、权限、状态同步和成本不一定是研究主题，却会直接改变用户看到的行为。

### 7. 用户结果：不是“生成完成”就算完成

真正要看任务有没有完成、外部状态是否正确，以及用户是否得到想要的结果。

### 8. 评估与学习：怎么发现问题、避免再犯

可以结合规则检查、实际执行结果、LLM Judge、人工审核和在线指标来判断。发现失败案例以后，还要补测试、改数据或调整策略，避免下次再犯。

## 例子：能查询订单并执行退款的客服 Agent

这类系统不能只生成自然语言。它要读取不断变化的业务事实，并可能执行有副作用的动作：

```text
用户消息
→ 语言、意图与风险识别
→ 结构化会话状态
→ 检索订单、物流、政策与商家证据
→ 模型决定回复、追问或调用工具
→ 执行层校验权限、schema、政策与必要确认
→ 执行 read / write tool
→ 基于执行结果生成回答
→ 置信度检查、澄清或转人工
```

订单、物流和退款规则随时可能变化，不能只靠模型“记得”。处理请求时，需要通过检索或工具调用查最新状态。后训练教的是**怎样依据这些信息作答、执行操作**，不是把业务数据库装进模型参数里。

不同信息要分开存：最近几轮对话帮助模型接上话；任务状态保存订单 ID、已验证的身份、工具结果和待确认操作；长对话摘要记录已确认的事实和还没解决的事。订单、物流和退款规则仍要查数据库，不能只相信摘要。

退款会改变真实的业务状态。执行前要检查权限、参数格式和必要的用户确认，并保留审计日志。若接口支持幂等键，同一笔退款的重试要复用原键和相同参数，并核对接口的作用范围与保留期限；随手生成一个新键不能防止重复退款。超时不代表操作一定没执行，重试前要查询状态或依赖已核实的幂等保证；信息不足、规则冲突或风险过高时，应先追问或转人工。具体语义取决于接口，例如 [Stripe 的幂等请求说明](https://docs.stripe.com/api/idempotent_requests)，不能把一个服务的保证套给所有工具。

这些校验由可信执行层落实，不能只在 prompt 里提醒模型。比如商家备注写着“忽略退款上限”，它仍是待核实的数据，不会因此变成政策或授权；JSON 格式正确也不代表当前用户有权退这笔款。检索内容和工具返回中的指令不能提升权限，模型评分也不能替代权限校验，参见 [OWASP 的 Agent 工具防护建议](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html#agent-specific-defenses)。

评估时要看任务有没有解决、回答有没有依据、是否遵守业务规则、工具参数是否正确，以及有没有不安全的操作。还要检查多语言表现、转人工是否及时、延迟和成本，并结合满意度（CSAT）及重复咨询率。回答自然只是其中一项。

## 不同问题，要用不同的检查方法

确定性规则、参考答案或执行器、LLM judge、人工审查和线上指标，各适合回答什么、不能凭它断定什么，[评估分层](../07-evaluation/evaluation-stack.md#check-methods)用一张表列清了。原则是能用规则准确判断的条件，不交给模型猜。真要让模型打分，先写清标准，再决定给单个回答打分还是比较两个回答；成对比较要交换展示顺序，并允许“平局”和“两者都不好”，见 [LLM judge 的打分格式](../07-evaluation/llm-as-a-judge/scoring.md)；怎样用人工标注校准、分组核对一致性，见 [LLM-as-a-judge](../07-evaluation/llm-as-a-judge/README.md)。

## 为什么要看完整链路

系统里的错误会向后传播：

```text
错误或缺失的数据
→ 错误的用户状态
→ 错误的 query
→ 错误的检索结果
→ 模型在错误上下文里做出“合理”决定
→ 最终体验失败
```

模型即使根据收到的信息作出了合理判断，也可能因为前面的信息错了，把整件事做错。

## 排查前，先问自己这九个问题

```text
Goal        真正想改善什么？
User        对谁改善？有没有被平均值遮住的群体？
System      数据、组件和控制流怎样连接？
Invariant   哪些性质绝对不能破坏？
Failure     具体在哪里、怎样失败？
Hypothesis  我认为原因是什么？什么结果会推翻它？
Constraint  延迟、成本、硬件、隐私和兼容性限制是什么？
Evidence    用什么证据判断修复有效？
Tradeoff    改善了什么，又可能伤害什么？
```

这不是为了把简单问题写复杂，而是避免只修最显眼的症状。目的也不是把每一层都学精，而是深入其中一层时，别丢掉整条链路的上下文。

## 两个帮助系统持续改进的模块

### Agent Observability：先看见发生了什么

它把模型、检索、工具、记忆和状态变化串成可查询的轨迹，再用这些记录构造受控回放测试。

→ [阅读 Agent Observability](agent-observability.md)

### Human-in-the-Loop：什么时候请人帮忙判断

不是每一步都要找人，而是遇到高风险操作、证据不足或没处理过的任务时，请人确认、纠正或接管。

→ [阅读 Human-in-the-Loop](human-in-the-loop.md)

<figure class="worked-update" id="action-control-flow" lang="zh-CN">
<figcaption>一个动作怎样从提议走到执行</figcaption>
<ol>
<li><strong>1 · 先说清要做什么</strong><span>记录目标、参数、依据和工具状态。模型可以提议动作，但提议本身不带执行权限。</span></li>
<li><strong>2 · 有没有权限？</strong><span>执行层检查权限与业务规则。不允许就停止或请求补充授权，不能让模型评分绕过这一关。</span></li>
<li><strong>3 · 要不要请人判断？</strong><span>先做确定性检查；需要评分时使用经过校准的 evaluator。规则要求确认、风险高或证据不足时，进入第 4 步；否则进入第 5 步。</span></li>
<li><strong>4 · 按人的决定分支</strong><span>批准后进入第 5 步；修改目标或参数就回第 1 步重新检查。拒绝或确认超时则停止，记录决定和原因。</span></li>
<li><strong>5 · 写入前再核对</strong><span>具体动作、授权、必要批准和当前状态都仍有效，才能执行。用版本条件或原子操作防止并发更新把检查与写入拆开；校验不通过就停止。</span></li>
<li><strong>6 · 检查结果，留下记录</strong><span>核对外部状态，不把超时当成成功或失败。执行和停止都要留下适当记录；发现的问题用于回归测试和后续策略更新。</span></li>
</ol>
</figure>

人工审核适用于高风险、证据不足或不可逆等情况；需要确认的动作还必须有有效批准。批准后改了目标或参数，要按新动作重新校验，不能沿用旧确认。图里展示的是控制关系，不是可直接部署的安全实现。
