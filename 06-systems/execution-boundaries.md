# 从 worker 到 GPU：谁在执行，谁在调度

**中文** · [English](execution-boundaries.en.md)

“GPU 空着，任务为什么还在等？”可能是任务根本没分到设备，也可能是模型在等数据、请求在等 KV 缓存空间，或某个训练进程还没等到一起通信的其他进程。只看 GPU 利用率，分不清这些原因。我们先看一次计算怎样交给设备执行，再看请求和作业会在哪里排队。

第一次读，可以先看运行时这一节；学过多卡训练后，再回来看集群调度。文中的机器拓扑、作业和流量都是为讲解而设的例子，用来说明各层怎样配合，不是集群实测结果。资料核对日期：2026-10-30。

## 运行时：一行 Python 怎样交给 GPU 执行 {#runtime}

### 先分清 CPU、GPU 和显存

训练程序首先是一个运行在 CPU 上的进程。它读取配置、准备数据，并把需要加速的计算交给 GPU。GPU 上有执行计算的单元，也有保存参数、激活和其他张量的设备内存。这里讨论的是独立 GPU，可以先把显存理解为 GPU 存放计算所需数据的地方。

`tensor.device` 告诉你张量当前在哪个设备上。CPU 中的 token 数组不会因为机器装了 GPU，就自动成为 GPU 可用的输入。程序和框架需要决定张量放在哪个设备、何时拷贝，以及计算开始前要等哪些数据就绪。

### 沿着一个算子往下走

假设 Python 里执行一次矩阵乘法。框架要先根据输入形状和数据类型选择合适的实现，再提交给设备执行。设备上实际运行的计算程序称为 kernel，也就是核函数：

```text
CPU 进程准备张量与依赖
  → PyTorch / 编译器 / 算子库选择或生成实现
  → CUDA 提交 kernel、拷贝等工作
  → GPU 执行，读取与写回设备内存
  → 需要结果时，通过依赖或同步确认完成
```

箭头表示这次计算经过的步骤，不是说每一步都需要一个单独的进程。一个进程可以负责其中多步，不同算子也可能使用不同的库。

### 提交、执行、等待结果，是三个时刻

CPU 上的调用返回时，GPU 可能正在执行，也可能还没开始。CPU 进程可以在这段时间准备其他数据；等后续计算真正需要结果时，再通过依赖或同步保证前面的工作已经完成。

CUDA stream 可以理解为提交工作的一条有序队列，也称为流。同一条流内的工作按相应顺序执行，不同流之间则需要根据数据依赖安排先后。GPU 内的计算单元称为 streaming multiprocessor，简称 SM，中文是流式多处理器。一条流并不固定占用一组 SM。具体机制见 [CUDA 编程模型](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html)与[异步执行](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)。

假设 `inputs=[[1,2],[3,4]]` 和 `weights=[[1],[2]]` 已在同一张 GPU 上。把乘法与后续求和提交到同一条流；乘法的形状是 `[2,2] @ [2,1] → [2,1]`：

| 时刻 | CPU 做什么 | GPU 上的结果与依赖 |
| --- | --- | --- |
| 提交乘法 | 调用 `outputs = inputs @ weights` 后继续工作 | 完成后得到 `[[5],[11]]`；调用返回时未必算完 |
| 提交求和 | 无须先等乘法完成，就调用 `total = outputs.sum()` | 求和排在乘法之后，得到 16 |
| 使用结果 | 在 CPU 上读取 16 | 等相关计算完成、结果传回后，才能安全使用 |

因此，只用 CPU 时钟测量一次异步调用，测到的可能主要是提交所花的时间。要测设备执行时间，需要根据实验目的使用 CUDA 事件（events）计时，或在合适的位置同步；要测完整服务的耗时，还得算上排队、输入和输出。还要说清楚，是否算上预热（warmup）、编译和图捕获（graph capture）所花的时间。[CUDA Graph](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/cuda-graphs.html)可以减少重复提交的开销，但不会消除显存占用，也不会省掉通信和算术运算本身的成本。

基础机制继续读 [CUDA：线程、内存与 kernel](../12-infra/cuda.md)和[框架这一层](../12-infra/frameworks.md)。

## 调度时，各层分别安排什么 {#scheduling}

### 先看每层安排的对象

集群调度器为作业分配设备，分布式运行时管理执行任务的 worker 进程，推理引擎决定本轮处理哪些请求，最后设备执行已提交的计算。这里说的“分布式运行时”主要管理进程和任务，前一节则是跟着单个算子看它怎样执行。每层掌握的信息不同，能做的决定也不同。

| 层次 | 安排什么 | 要看哪些资源和限制 | 等待的例子 |
| --- | --- | --- | --- |
| 集群作业 | Pod、Job、分布式作业 | 可分配 CPU/GPU、内存、配额、节点与拓扑 | 需要八张卡，却只有四张满足条件 |
| 分布式运行时 | Ray task / actor 等 worker 任务 | 逻辑资源、placement group、进程的启动、运行与退出 | 找不到能同时容纳 worker 所需资源包的位置 |
| 推理引擎 | 请求、序列、本轮 token | token 预算、KV 空间、prefill/decode 状态 | 新请求排队，已有请求继续解码 |
| 设备执行 | 已提交 kernel 的 thread blocks 等 | SM、寄存器、shared memory、依赖与可用资源 | 所需数据或前面的计算尚未完成，或资源不足以并发执行 |

### 集群层：把设备交给作业

在 Kubernetes 里，Pod 是运行容器的基本单位；[Job](https://kubernetes.io/docs/concepts/workloads/controllers/job/) 常用于做完就结束的任务，[Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) 常用于让服务副本持续运行。Slurm 则通过作业和资源分配来组织计算。先想清楚“需要多少设备、运行哪些进程、什么时候算完成”，再选具体的部署工具。

### 运行时与引擎：把资源用在当前工作上

Ray task 是一次远程函数调用；[actor](https://docs.ray.io/en/latest/ray-core/actors.html) 则是会保留状态的 worker，比如一直持有模型、连续处理请求的进程。放置组（placement group）描述一组资源包（bundle）需要怎样分配到机器上。这一层主要决定在哪里运行 worker。

vLLM/SGLang 的调度器还要看请求算到了哪一步：预填充处理输入提示，解码（decode）则逐步生成后续 token。引擎根据这些进度、KV 缓存空间和本轮 token 预算，决定把哪些请求放进本轮计算批次。

例如，worker 已拿到 GPU 并加载好模型，新请求 R 却还在等 KV 空间。设备已经分配，进程也已启动，但只有引擎把 R 选入批次后，才会提交它的计算。此时应查看引擎队列和 KV 使用情况，找出请求为什么还在等。

所以，“加一个服务副本”和“把引擎 batch 调大”效果不同。前者增加一组处理请求的资源，后者让已有资源处理更大的批次，也会影响排队时间、显存占用和单个请求的延迟。

### 设备层：执行已经提交的工作

CUDA 程序指定要执行什么、先后依赖是什么，GPU 内部的执行安排则由硬件和驱动等机制完成。这与 Kubernetes 决定把 Pod 放在哪台机器上，不是同一种调度。Ray 的逻辑资源声明也不能提供完整的显存保护或物理隔离，见[资源文档](https://docs.ray.io/en/latest/ray-core/scheduling/resources.html)。

Kubernetes、Slurm 和 Ray 也不是每个系统都必须依次经过的三层。可以直接用 Slurm 启动训练，也可以在 Kubernetes 上运行 Ray，由 KubeRay 管理 Ray 集群工作负载。具体选择见 [Ray on Kubernetes](https://docs.ray.io/en/latest/cluster/kubernetes/index.html)和已有的 [Kubernetes 笔记](../12-infra/kubernetes.md)。

## 有八张卡，还要看它们怎么连接 {#topology}

### 从进程组走到物理机器

假设两台机器各有四张卡。对一个 TP=4 的张量并行组，如果能把四张卡放在有高速互联的同一节点上，通常值得与跨节点的方案做个比较。不过，必须核对实际的 NVLink / PCIe 连接方式，不能只看节点名称。节点间的网络、NIC 网卡、NUMA 内存布局和存储，也会影响通信和数据读取。

双卡 TP 需要两张卡合作处理一个请求，和两份 TP=1 副本分别接请求不同。训练中，TP、流水线并行 PP 和数据并行 DP 怎样分组，又决定了通信频率和传输的数据类型。先画好[八卡分组](megatron-basics.md#eight-gpus)，再决定每组放在哪些节点上；Kubernetes 不会替模型推断最优的并行布局。

### 卡够了，作业也可能还在等

假设一个八卡训练作业必须由全部进程一起参与计算，每个进程在通信组内都有自己的编号，称为 rank。集群只有四张卡可用时，只启动一半进程并不意味着训练就能正常推进。成组资源申请和准入机制可以处理这类需求：把所需资源作为一组申请，再判断作业何时可以启动。具体行为取决于运行时和调度配置。

此外，还要检查设备类型、节点限制、配额和拓扑。有八张“空闲卡”，不等于八张都满足同一个作业的要求。

GPU device plugin 让作业可以申请 GPU，但申请成功不表示模型一定放得下、NCCL 一定能互通，或吞吐一定达标。见 [Kubernetes GPU 调度](https://kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/)。MIG、time-slicing、MPS 各有不同的隔离和共享方式，不能理解成把 80 GB 显存随意切成几份。

## NCCL：进程之间怎样交换数据 {#communication}

进程拿到设备后，还可能需要等待其他进程的数据。NCCL 是常用的 GPU 通信库；下面这些集合通信操作说明了参与进程怎样交换或合并张量。

| 原语 | 直观含义 | 一个训练用途 |
| --- | --- | --- |
| All-reduce | 按指定运算合并各 rank 的数组，再把结果返回所有参与者 | 同步对应梯度 |
| All-gather | 收集分片，让各参与者拿到拼接结果 | 按需取得完整参数组 |
| Reduce-scatter | 先按指定运算合并数组，再把结果分片交给各参与者 | 保存自己负责的梯度分片 |
| All-to-all | 各参与者向其他参与者发送不同部分 | 某些 MoE 实现中的 token dispatch / combine |

### 用两个小数组看通信的结果

设 rank 0 持有 `[1,2]`，rank 1 持有 `[3,4]`。每一行都从这两份原始输入重新开始：

| 操作 | 中间怎么算 | rank 0 最后持有 | rank 1 最后持有 |
| --- | --- | --- | --- |
| 求和 all-reduce | 对应位置相加：`[1+3,2+4]=[4,6]` | `[4,6]` | `[4,6]` |
| All-gather | 按 rank 顺序拼接，不求和 | `[1,2,3,4]` | `[1,2,3,4]` |
| 求和 reduce-scatter | 先得到 `[4,6]`，再等分给两个进程 | `[4]` | `[6]` |

如果训练目标需要两份等权梯度的平均值，就还要把求和结果 `[4,6]` 除以 2，得到 `[2,3]`。这里指定的是求和操作，不会自动完成这一步归一化。

这些原语只说明“最后谁拿到什么”。什么时候调用、传输哪组参数或梯度，以及能否一边通信一边计算，则由训练框架决定。

### 所有参与者需要遵守同一份约定

具体使用哪种通信操作，取决于训练策略。调用 NCCL collective 时，参与进程的调用顺序、元素数量 count、数据类型 dtype 等必须相互匹配。例如，rank 1 在反向传播时先发生 OOM 并退出，rank 0 随后等待梯度 all-reduce；最后看到的却可能是 rank 0 的通信超时。因此，排查 hang 这类卡住不动的问题时，要找所有进程中最早出现的异常，而不只看最后超时的那张卡。具体要求见[官方 collective 说明](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)。

## 从故障现象找到该查的地方 {#debugging}

| 现象 | 先检查什么 | 不能直接得出什么结论 |
| --- | --- | --- |
| Pod Pending | 调度事件、配额、资源请求、节点条件 | CUDA kernel 有 bug |
| Pod Running，模型迟迟未就绪 | worker 的启动、模型加载、预热和健康状态 | 已经能处理有代表性的请求 |
| GPU 空闲但请求堆积 | CPU 分词、数据准备与环境交互的耗时、队列、引擎预算 | GPU 算力不足 |
| CUDA OOM | 同一时刻的参数、激活、KV、缓冲区占用与内存分配器记录 | 只要增加 DP 进程就能解决 |
| NCCL timeout | 每个 rank 最早出现的错误、集合通信的调用顺序与拓扑 | 一定是网络故障 |
| 生成完成但客户端超时 | 请求截止时间、取消情况、流式回传与代理日志 | 模型计算没有完成 |

Pod 重建、Ray actor 重启和恢复训练，也是三件不同的事。重新启动进程后，还要恢复模型和优化器状态、随机状态，以及数据读到了哪里。强化学习还可能需要恢复尚未使用的采样轨迹（rollout）和策略版本，并记录哪些结果已经确认使用。平台可以重启进程，但无法补回应用没有保存的状态。

## 怎么判断一次优化值得做 {#measurement}

先把 CPU 执行、GPU 计算、通信和排队画在同一条时间线上，找出哪些步骤决定总耗时，再只改一个变量。例如，比较两个推理批次预算时，要保持模型、输入提示和输出的长度分布、精度、请求到达率和 GPU 拓扑一致。除了平均 tokens/s，还要同时记录吞吐、p50/p95/p99 延迟，以及失败和取消的情况。

比较训练方案时，则要保证有效批大小、损失归一化方式和更新次数一致，并按相同的质量要求检验结果。单卡上的张量对照不能证明多机训练能应对故障；小模型显存用得更少，也不能代替完整训练方案的吞吐实验。先在本机检查形状和事件顺序，再设好预算，用真实设备验证。排查等待时，先分清是在等资源分配、请求组批、设备执行还是通信，再选择要查的日志。
