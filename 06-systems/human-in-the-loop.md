# Human-in-the-Loop：什么时候应该让人介入？

**中文** · [English](human-in-the-loop.en.md)

## HITL 是一种风险控制策略

Human-in-the-Loop 不是“模型不会就全部交给人”，而是让系统在**风险高、证据不足、任务新颖或行动不可撤回**时，主动请求确认、纠正或接管。

## 先看一个需要升级给人的场景

让模型“帮我写一封邮件”和“直接替我发送这封邮件”看起来很接近，但风险完全不同。

- 写草稿：错了还可以修改，通常能自动完成。
- 发送邮件：会影响真实关系，最好先让用户确认。
- 批量发送给客户：影响更大，可能需要额外权限和专家审核。

HITL 的关键不是模型置信度低就问人，而是同时看**出错概率、影响大小和行动是否可逆**。

## 人在系统里可以扮演什么角色

| 角色 | 做什么 |
| --- | --- |
| 老师 | 提供示范、偏好、纠正和解释 |
| 审核者 | 检查高风险输出与关键行动 |
| 批准者 | 在产生外部副作用前授权 |
| 合作者 | 和模型一起补充上下文、拆解问题 |
| 审计者 | 定期寻找自动系统和 evaluator 的盲区 |
| 用户本人 | 表达目标、设置边界并纠正个性化状态 |

## 什么时候值得升级给人

可以用一个简单直觉理解：

> **介入价值 ≈ 出错概率 × 影响大小 × 不可逆程度 − 人工成本**

常见触发条件包括：

- 多个模型或 evaluator 结论明显冲突；
- 输入超出历史分布，系统以前没处理过；
- Search 找到的证据互相矛盾或不够可靠；
- 行动会发消息、花钱、修改数据或影响他人；
- 用户目标不明确，继续猜测的代价很高；
- Agent 进入循环、连续 fallback 或成本异常。

## 人工反馈不能只保存一个标签

如果审核者只点“同意 / 不同意”，模型以后仍然不知道错在哪里。

一次有用的人工介入应该尽量保存：

- 为什么这个案例被升级；
- 审核者看到了哪些证据；
- 最后做了什么决定；
- 修改了模型输出或行动的哪一部分；
- 为什么这样修改；
- 这个案例应该更新测试、规则、policy 还是训练数据。

## 三种介入时间

### 实时确认

行动发生前让用户批准，适合高风险或不可逆操作。

### 事后抽查

从完成的轨迹中抽样，发现系统性失败、judge 偏差和新类型问题。

### 定期重新设计规则

随着模型和任务变化，重新检查 rubric、升级阈值、权限、数据保留和用户控制。

## 常见误区

- **把人当成 fallback API**：没有提供上下文，却要求快速做决定。
- **只看最终回答**：忽略 Search、工具、副作用和状态更新。
- **只收标签，不收理由**：后续无法形成清晰学习信号。
- **升级规则永远不变**：模型能力和任务风险变化后仍使用旧阈值。
- **反馈直接进入训练**：没有处理标注者差异、策略偏置和数据泄漏。
- **自动化偏见**：模型语气越自信，人越容易不加思考地接受。

## 好的 HITL 最终应该减少什么

目标不是让越来越多任务依赖人工，而是让最有价值的人类判断出现在正确位置，然后把这些判断变成：

- 新的确定性规则；
- 更好的 eval case；
- 更清楚的失败 taxonomy；
- 可复用的训练数据；
- 更合理的自动化边界。
