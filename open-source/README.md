## 为什么要往上游提交

自己的仓库里，代码只要说服自己就行。往别人的代码库提交，要说服的是一个不认识你、没时间、而且默认你是错的人。这两件事需要的能力完全不同。

上游贡献强迫你回答几个在自己项目里可以绕过的问题：

- **这个改动为什么是对的？** 不能说“我跑了一下没事”。要给出别人不跑也能验证的论证。
- **它会不会破坏我不知道的东西？** 一个几万行的库里，你改的函数有五个调用点，其中三个你从没读过。
- **怎么让人相信？** 同一个事实，写成“我优化了性能”和“这个张量的 94% 被算出来又扔掉，而且被丢弃的列在数学上影响不了留下的列”，得到的回应完全不同。

对我来说，这是**检验自己是不是真的读懂了**最便宜的方式。看懂一篇论文很容易骗自己；在一个真实的训练框架里指出“这一项是多余的”并让维护者接受，骗不了。

## 这个栏目写什么

不写“我提交了几个 PR”。写的是：

- 这个库在整个系统里是干什么的，它的难点在哪
- 每个改动背后的**判断过程** —— 为什么怀疑这里有问题、怎么证明的、哪些猜测被自己推翻了
- 做错的地方。有几次我把一个不成立的结论差点写进公开评论

## 一条贯穿的线索

回头看，我提交的东西里绝大多数不是“写错了”，而是两类：

**代码在做一件它不需要做的事。** 算了一个会被抵消的归一化常数；把整个词表物化出来只为读其中 64 列；把一个矩阵投影到 128k 维再切出 8k 维。

**代码没做它声称在做的事。** 一个函数打印“正在 mask 掉这些位置”，算出了 mask，然后把它扔了；一个配置项文档里写着、代码里接受、但从来没被读过；一句精心写好的报错永远不可能执行到。

这两类问题**读代码就能证明**，不需要 GPU、不需要跑实验、不需要论文支持。这也是为什么一个只有一张消费级显卡的人，能在一个为集群设计的框架里持续找到东西。
