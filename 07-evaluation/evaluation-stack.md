# 分层评估：哪些检查先做，哪些需要更多投入？

**中文** · [English](evaluation-stack.en.md)

一套评分方法很难回答所有问题。下面按通常需要的投入，分成五类。实际成本会随任务变化；能用简单检查解决的，就不用一开始交给更贵的方法。

## 1. 确定性检查

字段和格式是否正确、状态有没有按预期改变、工具参数是否合法、权限是否足够，这些通常可以用代码检查，不必让模型猜。

## 2. Reference 或 Executor

代码可以跑测试，数学题可以核对答案，检索结果可以检查证据，Agent 可以验证任务是否完成。这类信号通常比语言评分更接近真值。

## 3. LLM-as-a-Judge

适合相关性、帮助性、连贯性、风格和开放式质量。它能扩展到大量样本，但会受到 prompt、模型版本、位置和表达风格影响。

## 4. 人工审查

人工适合帮忙定评分细则、检查边界案例，也能发现自动评估没覆盖的问题。不同人可能判断不一，所以要先讨论标准，再记录各自的理由。

## 5. 在线与长期结果

最终还要看真实任务完成、用户纠正、重复使用和长期行为。离线指标改善不一定会转化为更好的体验。

## LLM Judge 应该怎样用

可以请 LLM Judge 帮忙判断含义和质量，但它的评分也需要验证，不能当作标准答案。

更稳健的做法包括：

- 一次只判断一个清楚的问题；
- 有可靠参考答案时，提供给模型对照；
- 比较两个方案时交换 A/B 顺序；
- 允许 `tie` 和 `both bad`，不要强迫选赢家；
- 用人工标注样本，检查哪些任务或人群上容易评错；
- 保存提示词、模型版本、采样温度和输入依据；
- 不要求 judge 编造看似精确但没有依据的 1–10 分。

把 rubric 写成 DAG 可以帮助拆分判断，但 DAG 本身不会自动让指标正确。最重要的仍然是每个节点是否对应真实、可验证的标准。
