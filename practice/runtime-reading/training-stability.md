# 训练为什么不稳定：从样本查到一次更新

**中文** · [English](training-stability.en.md)

看到损失（loss）上下波动，很容易先怀疑学习率太大。有时确实如此，但也可能是长短样本的权重变了、填充位置（padding）误算进了损失、低精度中间值溢出，或者训练收到的采样记录（rollout）越来越旧。曲线看起来相似，原因未必一样。

下面先用 `A B C D → E F G` 检查模型在学哪些位置，再算清楚损失该除以多少个 token，最后排查数值计算、RL 数据和训练恢复。可以先找与自己遇到的问题最接近的一节，不必一上来就改动整套训练配置。

## 先说清“不稳定”指什么 {#symptoms}

| 观察到什么 | 先判断什么 | 可以从哪里查起 |
| --- | --- | --- |
| 损失变成 NaN / Inf | 第一个非有限值出现在哪里 | 保留出错的批次；逐段检查输入、logits、损失和梯度 |
| 损失波动或突然变大 | 这批数据更难，还是更新幅度变了 | 有效 token 数、数据子集、学习率、裁剪前梯度范数 |
| 损失持续下降，验证效果变差 | 过拟合、数据泄漏、目标算错，还是评估方式变了 | 固定验证集、同一生成配置、失败样本 |
| 奖励上涨，实际回答变差 | 奖励被钻空子，还是输出分布变了 | 独立评估、长度与截断率、各项奖励 |
| 训练突然停住 | 算法没有学习信号，还是进程在等待其他任务或通信 | 各工作进程的阶段、队列、集合通信顺序和超时 |

随机梯度本来就会有噪声。不能只因曲线不够平就判定失败，也不能因为训练一直没报错就认为结果可靠。比较相同任务上的质量和成本，同时保留能回放的具体样本。

## 模型到底在学哪些位置？ {#masks}

设输入是四个提示 token 加三个回答 token。做下一 token 预测（next-token prediction）时，D 位置预测 E，E 位置预测 F，F 位置预测 G；因此，回答的三个目标与用来预测它们的 logits，要在序列中错开一位。

先只算回答 E、F、G，暂不加入结束符（EOS）。把预测位置和目标并排放，比只看两个长度相同的张量更容易发现错位：

<div class="compact-table" markdown="1">

| 预测位置 | 下个目标 | 计入损失？ |
| --- | --- | --- |
| A | B | 否 |
| B | C | 否 |
| C | D | 否 |
| D | E | 是 |
| E | F | 是 |
| F | G | 是 |

</div>

“预测位置”指使用哪个位置的 logits。前三行的目标还在输入提示中，不计入回答损失；D 位置预测的 E 则是回答的第一个 token，要计入。

这里对齐的是六对预测与目标，损失掩码（loss mask）是 `[0, 0, 0, 1, 1, 1]`。如果从 E 位置的 logits 才开始算损失，会漏掉“给定整个输入提示后预测 E”这一项。完整样本中的 EOS、截断和工具返回，还要按各自的目标处理。

再把这个区别推广到实际样本：

| 内容 | 可以作为上下文吗？ | 是否计入这次策略或回答的损失？ |
| --- | --- | --- |
| 用户输入 | 可以 | 取决于训练目标；只训练回答部分的 SFT 通常不计 |
| 模型生成的回答 | 可以 | 有效动作或目标位置计入 |
| 工具返回的内容 | 可以 | 通常不是策略采样的动作，不能直接当动作训练 |
| 填充位置 | 只是对齐用途 | 不计入有效目标 |

**注意力掩码（attention mask）和损失掩码不是同一个东西。** 某段文本可以作为注意力的上下文，却不参与当前损失。把多个样本打包（packing）到同一序列时，还要防止相邻的独立样本互相看到不该看的上下文。

检查时，把一条实际样本打印成 token、目标、注意力边界、损失掩码四列，而不只是确认张量形状相同。NeMo RL 中可以沿 [`prepare_loss_input`](https://github.com/NVIDIA-NeMo/RL/blob/1c4020163a5523be4365de7fdeaa411770ecc589/nemo_rl/algorithms/loss/loss_input.py#L199)查看目标偏移和掩码的处理；SFT 的数据规则见[数据与目标](../post-training/data-and-objectives.md)。

## 拆成微批次后，损失该怎么平均？ {#normalization}

假设选择的目标是**所有有效 token 的平均损失**。微批次 A 有 100 个有效 token，平均损失为 1；B 有 10 个，平均损失为 3。

$$
\begin{aligned}
L_{\mathrm{token}}&=\frac{100\times1+10\times3}{110}=\frac{13}{11}\approx1.182,\\
L_{\mathrm{batch}}&=\frac{1+3}{2}=2.
\end{aligned}
$$

第二个式子让只有 10 个 token 的 B 和 A 占同样权重。按微批次平均未必总是错的，但它**不是前面选定的逐 token 平均目标**。两种算法得到的损失数值也不能直接比较。

具体到一个 token：先各自取均值、再把两批平均，A 中每个 token 的权重是 `1/200`，B 中则是 `1/20`。B 的单个 token 被放大到了 A 的 10 倍。按全局 token 平均时，两边每个 token 都是 `1/110`。所以这不只是日志里的损失数字变了，梯度中各部分的相对权重也变了。

做梯度累积时，可以把每个微批次的损失总和，除以一次更新所用的整个逻辑批次的有效 token 总数，再累积梯度。这个总数必须事先知道，或通过等价方法处理；若每批 token 数不同，单纯把各自的均值除以“累积步数”不够。

<details markdown="1">
<summary>再到多卡：梯度归约的平均会不会多除一次？</summary>

假设数据并行组有 R 个进程（rank），梯度归约采用平均，总有效 token 数为 N。每个进程按下面的式子计算局部损失，归约后就能得到按全局 token 平均的梯度：

$$
\begin{aligned}
L_r&=\frac{R}{N}\sum_{i\in\mathcal{D}_r}\ell_i,\\
\frac{1}{R}\sum_r\nabla L_r&=\frac{1}{N}\sum_i\nabla\ell_i.
\end{aligned}
$$

这里假定数据不重复、R 是实际参与梯度平均的组内进程数，而且没有其他地方再次缩放。训练后端可能已经处理了归一化，不能不看代码就额外乘 R。即使某个进程没有有效目标，也不能擅自跳过其他进程正在等待的集合通信（collective）；如果整个逻辑批次都没有有效 token，就要明确处理这个空批次，不能继续除以零。

</details>

附带的[小实验](code/runtime_checks.py)会复算 1.182 与 2 的差别，再用预先给定的各进程梯度总和检查归约；它没有从平均损失数字反推出梯度。更完整的训练布局见[多卡训练](../../06-systems/distributed-training.md)。

## NaN 从哪里来？梯度裁剪能解决什么？ {#numerics}

二分类 logits 是 `[1000, 1001]`，正确类别是第二个。直接求两个 `exp` 很容易溢出，但稳定地减去最大值，交叉熵只有：

$$
\log\left(1+e^{-1}\right)\approx0.313262.
$$

所以发现 NaN 时，要先找到它第一次出现的位置，不要立刻把它替成 0。`log_softmax`、稳定的交叉熵和必要的高精度归约，能减少数值计算问题，却修不好错标签或错掩码。

混合精度下还要区分两种裁剪：**梯度裁剪（gradient clipping）**限制梯度范数；**PPO clipping**改变代理目标中的概率比值项。两者解决的问题不同，不能互相替代。

比如梯度向量是 `[3, 4]`，L2 范数为 5。若把范数上限设为 1，理想的范数裁剪会把整个向量乘以 `1/5`，得到 `[0.6, 0.8]`，方向不变；不是把每个分量截到 1 后得到 `[1, 1]`。实际实现可能加 epsilon 避免数值问题，见 [PyTorch 的范数裁剪接口](https://docs.pytorch.org/docs/2.15/generated/torch.nn.utils.clip_grad_norm_.html)。如果裁剪前就已出现 NaN，先查 NaN 的来源，不能指望这个缩放把它修好。

若采用 FP16 损失缩放（loss scaling），通常先累积完整逻辑批次中放大后的梯度，再还原缩放、检查并裁剪梯度、执行优化器更新，最后更新缩放器。累积到一半时改变缩放系数，会让前后梯度无法按原意相加。具体顺序参考 [PyTorch AMP 示例](https://docs.pytorch.org/docs/2.15/notes/amp_examples.html#gradient-clipping)。BF16 常常不需要同样的损失缩放，但也不能保证所有运算都不会溢出或丢失精度。

## RL 中，生成样本的模型也在变 {#rl}

监督学习可以反复用同一份数据；在线 RL 的策略变了，随后采到的答案、长度和成功率也会变。异步采样再加一层：正在训练的模型与生产样本的模型，可能已不是同一版。

先看一个概率比值。某个动作生成时概率为 0.2，当前模型给它 0.3，比值是 1.5。如果误用另一版模型的 0.25 作分母，就变成 1.2。数值仍然有限，代码也能跑，但你已经换了比较对象。完整的 behavior / old / current 区分见[异步 RL](../../06-systems/async-rl.md#objective)。

[PPO](https://arxiv.org/abs/1707.06347)的单项 clipping 可以用一个很小的数值例子理解：比值 1.5，裁剪区间 `[0.8, 1.2]`。

| Advantage | 未裁剪项 | 裁剪项 | 取较小值 |
| --- | --- | --- | --- |
| +1 | 1.5 | 1.2 | 1.2 |
| −1 | −1.5 | −1.2 | −1.5 |

正优势的例子不再奖励继续增大这个比值；负优势的例子仍保留变坏的惩罚。这个机制不是把所有动作概率硬限制在区间内，也不保证整体 KL 或模型能力永远稳定。

GRPO 还要看组内信息量：一组全是 0 或全是 1，减去组均值后的相对优势信号都是零；KL 或其他损失项仍可能有梯度。标准差很小也要检查数值处理，但简单提高 epsilon 不能制造新的有用反馈。

不要只看平均奖励。还要看组内奖励分布、有多少组的回答全都同分、有效动作数、输出长度与截断率、样本生成后经历了多少次策略更新，以及概率比值和裁剪比例（clip fraction），并与独立评估对照。若只保留最先完成的回答，模型可能逐渐更多地学到短任务；这首先是样本选择问题，不是加快 GPU 就能自动解决。

## 损失降了，模型真的更好了吗？ {#evaluation}

损失稳步下降，也可能学错了东西。比如清洗时滤掉了困难样本，平均训练损失会更好看；输出上限变短，单次采样更快，却可能截断长推理任务；负责解析答案和计算奖励的代码把错误格式判为正确，模型甚至可能很快学会利用这个漏洞。

保留一份固定的验证数据，同时检查近期线上流量中的代表性样本。比较不同检查点（checkpoint）时，使用相同的分词器、提示格式、采样设置和评分器，再检查失败样本。除了平均分，也要分别评估原有基础能力、目标任务，以及容易退化的长尾场景。

不是所有场景都需要微调或 RL。目标任务没有收益、基础能力却下降时，保留原模型就是有效结论。如何组织数据与独立验收，可继续看[数据流水线](../post-training/data-pipeline.md)与[实验和发布](../post-training/experiments-and-release.md)。

## 重启以后，真的接着上一次在训练吗？ {#recovery}

模型权重、优化器状态、学习率进度、随机状态和数据消费位置应相互匹配。RL 还可能有尚未完成的采样任务、队列中的样本数据、组索引与生成版本。只加载权重继续跑，可以算一次新实验，却不等于从中断处接着训练。

可以做一个小型中断实验：固定数据和配置，一组连续运行两次更新；另一组在第一次更新后保存并重启，再运行第二次。比较模型与优化器状态、用过的样本 ID、更新步数和结果；允许的差异取决于非确定性和恢复协议。异步系统不一定要求逐位复现，但至少要能解释哪些任务被丢弃、重复执行或重新采样。

因此，[NeMo RL 怎样管理一组样本的生命周期](nemo-rl.md#lifecycle)，会直接影响模型实际学了哪些数据，而不只是运维问题。持久化细节见[checkpoint 与恢复](../post-training/checkpoint-and-resume.md)。

## 排查时，一次只加回一项 {#debug-route}

1. 固定失败样本和配置，先核对 token、预测与目标的偏移、掩码和归一化分母。
2. 在小规模、高精度的配置下比较前向结果、损失和梯度；能过拟合一个小批次，可以帮助排错，但不能证明泛化能力。
3. 加回混合精度、样本打包和梯度累积，一次只改一项。
4. 再加多卡，检查归约、分片和恢复，而不是直接从大集群的曲线猜原因。
5. 对 RL，先用一份来源明确的固定采样记录检查损失，再接回在线生成、权重刷新和异步队列。
6. 最后比较相同质量门槛下的耗时、有效样本数、GPU 小时数和独立评估结果。

先在同一份小数据上解释差异，再逐步加回真实配置。这样即使还没有找到最好的超参数，也能知道自己这次改的是数据、目标、数值计算，还是执行方式，避免几种变化混在一条曲线里。
