# 实验怎么比较，模型怎么替换

**中文** · [English](experiments-and-release.en.md)

> 原创教学案例 · 最近核验：2026-10。下文通过率是手工构造的小表，用来解释比较方法，不是模型成绩。

跑完训练，最想看的通常是“涨了多少”。但总体从 60% 到 70%，还没告诉我们：哪些问题变好了？哪些原来能做的反而做错了？是不是评测时多给了一段提示？

## 先把实验设置存下来

先不用搭复杂的平台。把模型、数据和评估设置一起保存，之后才知道两次实验差在哪里。下面是一份简化的实验清单（manifest）：

```json
{
  "run_id": "citation-sft-demo-01",
  "base_revision": "local-fixture-v1",
  "data_snapshot": "examples-v3",
  "split_rule": "question-family-v1",
  "template_revision": "chat-template-v2",
  "objective": "assistant-target-token-mean",
  "eval_snapshot": "fixed-evidence-v2",
  "decode": {"sampling": false, "max_new_tokens": 128}
}
```

这是字段示意，字符串不是可下载的真实 checkpoint。正式运行还要存实际内容 hash、依赖版本、随机种子、优化器配置、训练步数和有效 token 数。实验 ID 是索引，不能代替内容快照。

如果 A 用了 128 个输出 token，B 用了 512 个，比较仍有意义，但回答的是“两个不同预算系统谁更好”，不是纯粹的训练收益。

## 总分涨了，哪些题变好了？

`1` 表示通过事先定义的检查，`0` 表示未通过。同一道题的新旧结果放在同一行：

| 问题 | 分组 | 旧模型 | 新模型 | 变化 |
| --- | --- | --- | --- | --- |
| q1 | 有证据 | 0 | 1 | 改善 |
| q2 | 有证据 | 0 | 1 | 改善 |
| q3 | 有证据 | 1 | 1 | 不变 |
| q4 | 有证据 | 1 | 1 | 不变 |
| q5 | 缺证据 | 1 | 0 | 回退 |
| q6 | 缺证据 | 1 | 1 | 不变 |

总体从 `4/6` 到 `5/6`，但看 q5：原来没资料时会说明情况，现在反而处理错了。缺证据这组从 `2/2` 降到 `1/2`。新模型可能更会回答，也可能只是更愿意回答。需要打开 q5 的具体输出，再检查训练中缺证据的示范是否足够、是否写得合适。

**配对比较（paired comparison）**保留同一道题的变化。这里两胜一负三平；六道题远不足以估计稳定提升，只适合说明怎么发现回退。真实比较还要报告样本量和不确定性；问题来自同一用户或文档时，重采样也要考虑这种分组相关性。

## 没跑完的题，单独记录

旧模型跑了 100 道，新模型只完成 80 道，直接对各自成功返回的部分取均值可能有选择偏差。我们的小程序遇到缺失 ID 会报错，要求先处理不完整的配对。

实际评测可以给每题保留 `ok / timeout / invalid_output` 等状态，再分两种角度报告：

- **用户能否得到可用结果？** 用全部请求作分母，超时、格式错误都影响成功率。
- **两者都正常完成时，哪个答得更好？** 比较双方均有有效输出的题，同时列出排除了多少题、为什么排除。这只是这个子集的表现，不能直接推广到所有请求。

两种角度都需要。超时不等于知识答错，但也不能在报告中消失；若任务明确要求 JSON，输出格式不合规本身也可以算一次任务失败。

```bash
python3 practice/post-training/code/experiment_checks.py
```

[代码](code/experiment_checks.py)会打印上面六道题的总体和分组结果。删掉一条新模型结果，会得到缺失配对错误；把一个问题族同时放进 train 和 test，会得到泄漏错误。

## 先小跑，再扩大训练

| 阶段 | 先检查什么 | 过关后才做什么 |
| --- | --- | --- |
| 单条 / 单 batch | token、mask、loss、梯度有限 | 极小数据训练 |
| 小数据 | 是否能学会几个明确示范；缺证据行为是否被破坏 | 扩大数据与训练时长 |
| 保存恢复 | 固定设置下的输出对照、优化器/调度器与必要随机状态 | 长训练与中断恢复 |
| 完整离线评估 | 固定协议、分组回退、资源代价 | 有明确回滚方案的受控发布 |

小数据上学不会，先排查输入、目标和实现，不要马上再加更多卡。反过来，小数据上背下来了也不证明能泛化；那只是训练路径的一次检查。

具体做法见[训练选型](training-plan.md)、[多卡与有效 batch](distributed-training.md)和[断点恢复对照](checkpoint-and-resume.md)。不要只记录“用了几张卡”：实际有效 target token、端到端耗时、显存峰值和失败重跑的代价也属于实验结果。

如果只能离线测，就停在离线结论。可以设计 user simulation 做压力测试，但模拟用户不能替真实用户证明产品收益。

## 换模型时，别漏掉模板和配置

除了模型权重，还包括 tokenizer、模板、生成参数、输入预处理和工具/输出 schema。只回滚权重而保留新模板，未必回到了旧系统。

先让新版本在不影响用户的 shadow 请求上跑同样输入，检查格式、延迟、错误类型；再按场景决定是否做受控在线验证。shadow 没有改变用户看到的内容，因此不能测出用户行为收益。预先写清停止条件，例如关键分组明显回退、输出格式错误超限或延迟超过产品预算。阈值由业务风险决定，不从这张六题表里拍出来。

如果关键问题还没解决，这轮就先保留旧版，把下一步要验证的假设写下来。实验的价值不只在于分数上涨，也在于弄清楚哪种改动值得继续做。
