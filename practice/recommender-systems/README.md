# 推荐系统拆解：从一条帖子，到整套架构

**中文** · [English](README.en.md)

刷到一条好内容，看起来只是“模型猜你喜欢”。但打分之前，系统就已经决定了去哪里找、哪些内容有资格出现；打分以后，还得把候选排成一屏。

我们从这里拆开：**每一层解决什么问题，为什么放在这里，换个做法会怎样。** 不用先背一串模型名。先跟一次请求走，再回来理解训练、内容更新和工程取舍。

## 先看全貌，点开一层试试

下面不是 Twitter / X 的生产拓扑，而是一套教学架构。切换 3 条路径，把“用户刷新”“内容更新”和“模型训练”分开。在线路径还可以改一个条件，看候选怎样消失。

<div class="widget" data-recsys-architecture><p>在线：请求 → 召回 → 去重与补特征 → 打分 → 列表 → 反馈。更新：内容变化 → 编码 → 索引 → 配套发布。学习：曝光与反馈 → 样本 → 训练 → 评估 → 配套发布。</p></div>

先记住：**一个框不一定是一台独立服务；更新内容向量，也不等于重新训练模型。** [架构导读](00-architecture.md)会展开这两个区别。

## 每一期解决一个问题

| 章节 | 这次要想清楚什么 | 读完试着做什么 |
| --- | --- | --- |
| [00 · 架构导读](00-architecture.md) | 请求、更新、学习怎样接在一起？ | 标出每个组件何时运行、交出什么 |
| [01 · 一次刷新](01-feed-pipeline.md) | 为什么推荐不是一个模型？ | 追踪一条候选的来源、特征和去向 |
| [02 · 多路召回](02-candidate-retrieval.md) | 多加一路到底补了什么？ | 固定预算，检查独有相关候选 |
| [03 · 排序与列表](03-ranking-and-diversity.md) | 单条不错，为什么一屏仍然无聊？ | 拖动惩罚权重，区分模型分数和列表选择 |
| [04 · 新方法放在哪](04-modern-recsys.md) | Transformer、生成式检索替换了哪一层？ | 把新模型放回架构，而不是只记名字 |
| [05 · 评估实验](05-evaluation-lab.md) | 分数变了，模型一定变了吗？ | 切换候选池、Top-K 和分母 |
| [06 · 为什么是双塔](06-why-two-towers.md) | 省掉什么计算，放弃什么交互？ | 比较一条混合查询与分开查询 |
| [07 · 组件怎么选](07-component-choices.md) | 同一个框有哪些合理实现？ | 先写约束，再写方案与退出条件 |
| [08 · 工程落地](08-serving-lifecycle.md) | 接口成功，为什么结果仍可能错？ | 检查版本、超时、新鲜度与回滚 |

每篇都沿着 **问题 → 做法 → 替代方案 → 代价 → 验证** 来讲。小实验用来理解机制，不是替真实用户作判断。
