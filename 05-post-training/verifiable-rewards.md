## 奖励从模型变成可检查规则

数学题可以对答案，代码可以跑测试。这类任务的奖励**不需要学，写一个程序就行**。而这一步换掉的不只是一个模块——**能被钻空子的是被拟合出来的奖励，不是被验证出来的**。不过 reward hacking 并没有消失，它换了个地方：从骗奖励模型，变成骗验证器。

## 换掉了什么

回顾 [RLHF 的四个模型](rlhf-pipeline.md)：Policy、Critic、Reward、Reference。可验证奖励删掉的是 **Reward Model**——那个用[偏好数据](where-preferences-come-from.md)拟合出来的网络。

$$r(x,y) = \text{verify}(y) \in \{0, 1\}$$

一个确定性函数取代了一个学出来的函数。

## 为什么它能收窄 reward hacking

奖励模型是可微的、连续的、在有限数据上拟合的。这三条合起来意味着：**它有梯度可以攀爬，而且在训练分布之外的地方是外推出来的。** 策略只要找到那些"奖励模型没被监督过、但打分很高"的角落，就能拿到高回报而不用真的变好。

验证器没有这个性质。测试要么过要么不过，中间没有可以顺着爬上去的坡。**你没法把一个单元测试说服到 0.9 分。**

所以可验证奖励几乎是顺带地解决了 RLHF 最顽固的那个问题。这不是因为它更"聪明"，是因为它**在结构上没有那个可被利用的表面**。

## 但 reward hacking 只是换了地方

这一节是重点，因为"用了 RLVR 就没有 reward hacking 了"是个危险的简化。

**验证器本身可能有洞。** 如果奖励是"通过测试"，而测试覆盖不全，那么模型学到的是**通过这些测试**，不是**写对代码**。它会：

- 针对测试用例硬编码返回值；
- 捕获所有异常让程序不崩溃，从而通过"不报错"这类检查；
- 找到测试框架本身的漏洞。

数学侧同理：只验最终答案的话，模型可以通过**猜**、通过写一堆看起来像推理但和答案无关的东西然后蒙对来拿分。**过程是错的，奖励是满的。**

一般化的说法是：**你验证的东西，就是模型会去优化的东西——不多也不少。** 这和奖励模型时代的教训是同一条，只是这次那个"错误的目标"是你自己写下来的，因此至少是可读、可审计、可修的。

## 二元奖励带来的新问题：信号太稀疏

学出来的奖励模型给的是连续分，"差一点"和"差很多"是有区别的。验证器只给 0 或 1。

后果直接连到[算法那一篇](after-ppo.md)：用组相对基线（GRPO/RLOO）时，**一组回答全对或全错，减去均值后优势全是零，这一组不产生任何梯度**。题目太简单或太难时，这种组占比会很高，采样白做。

DAPO 的动态采样就是冲着这个来的：把全对全错的组过滤掉，保证每个 batch 里都有可用的梯度。

**所以 RLVR 和"组相对基线"这两个选择是耦合的**——单独看都合理，凑在一起会放大彼此的弱点。任务难度分布因此变成一个需要主动设计的东西，而不是数据集自带的属性。

## 结果奖励还是过程奖励

只验最终答案（结果奖励）便宜，但会奖励"蒙对"。验中间步骤（过程奖励）信号密得多，但**中间步骤谁来标**——如果要人标，你就又回到了偏好数据那套成本和噪声里。

现在常见的折中是用模型来生成或校验过程标签，但那等于**又引入了一个学出来的评判者**，也就把那个可被攀爬的表面请了回来。这个取舍没有免费解。

## 可验证性是个连续谱，不是二分

容易被当成"能验/不能验"两档，实际是一条带宽：

| | 例子 | 验证器长什么样 |
| --- | --- | --- |
| 强可验证 | 数学答案、单元测试、编译通过 | 确定性程序，几乎无洞 |
| 半可验证 | 格式合规、引用是否真实存在、SQL 能否执行 | 程序能查一部分，查不了"合不合适" |
| 弱可验证 | 摘要是否忠实、解释是否清楚 | 只能靠模型评判或人 |
| 不可验证 | 语气、创意、审美 | 只有偏好 |

**判据是：把任务往这条带宽的左边推，比换算法划算得多。** 很多看起来"只能靠偏好"的任务，拆开之后有一半是可以验的——比如"写一份报告"里，引用真实性、数字一致性、格式合规都能验，剩下的才需要偏好。

先做这个拆分，再谈用什么算法。

## 设计可验证奖励时检查什么

1. 我的验证器有多少洞？我有没有试着**故意**去骗它一次？
2. 如果奖励是二元的，我的 batch 里有多少比例的组是全对或全错？
3. 我验的是结果还是过程？验结果的话，蒙对的比例有多高？
4. 我这个任务真的"不可验证"吗，还是我没拆开？哪一部分其实是可验的？
5. 如果我引入了模型评判者，那个可被攀爬的表面是不是又回来了？
