# 可验证奖励（RLVR）：测试通过了，任务就做对了吗？

<span id="_1"></span>

## 奖励从模型变成可检查规则 {#_3}

让模型写一个排序函数，可以请另一个模型判断“写得好不好”，也可以把结果拿去跑测试。后者把一部分判断变成了可重复检查的程序。

如果测试只包含 `[3, 1, 2]`，一直返回 `[1, 2, 3]` 也能过。换成空列表、重复元素或负数，这个实现就会出错。用这类检查结果作为奖励来做强化学习，称为 RLVR（Reinforcement Learning with Verifiable Rewards）。它的价值在于检查明确、方便复现，不在于天然没有漏洞。

## 换掉了什么 {#_4}

回顾[基于人类反馈的强化学习（RLHF）的四种角色](rlhf/three-stages.md)：策略模型生成回答，价值模型估计回报，奖励模型评分，参考模型用于约束策略变化。对于能用规则检查的那部分目标，可以用验证器代替从[偏好数据](where-preferences-come-from.md)学出的奖励模型；其他目标仍可以用人或模型评价，不必让整个系统只用一种奖励来源。

$$r(x,y) = \operatorname{verify}(x,y) \in \{0, 1\}$$

这里 $x$ 包含题目及检查所需的上下文，$y$ 是候选回答。0/1 只是一个例子，也可以用通过测试的比例或多项分数。结果能否复现，还取决于测试输入、运行环境、随机种子和超时设置是否固定。可验证奖励描述的是奖励来源：既可以配合近端策略优化（Proximal Policy Optimization，PPO），也可以配合组相对策略优化（Group Relative Policy Optimization，GRPO）。**它本身不规定优化算法，也不决定是否要训练价值模型。**

## 为什么它能减少一类奖励投机 {#reward-hacking}

用测试替换奖励模型后，就能直接检查代码的部分行为，而不只是让另一个模型根据回答内容判断正确性。测试检查的性质更明确，失败也更容易复现，因此能减少一类奖励模型泛化错误。

但“奖励是离散的、不可微”并不能阻止模型钻空子。策略梯度（policy gradient）根据采样结果的奖励调整生成概率，不需要对测试程序本身求导。能通过不完整测试的错误实现，仍可能被逐渐强化。

## 规则也可能漏掉真正的要求 {#reward-hacking_1}

奖励投机（reward hacking）指模型获得了更高的代理奖励，却没有更好地完成实际目标。奖励不必来自神经网络，手写规则也可能给错激励。

如果检查覆盖不全，训练可能强化这些本来不想要的行为：

- 针对测试用例硬编码返回值；
- 捕获所有异常让程序不崩溃，从而通过“不报错”这类检查；
- 找到测试框架本身的漏洞。

这类漏洞已有实测案例，见前沿草稿[智能体强化学习：环境与奖励从哪里来](../11-frontier/agentic-rl/environments-and-rewards.md)。另一个要区分的问题是：训练后准确率提高，并不足以证明奖励本身提供了有效的正确性信息。

[Spurious Rewards（Shao 等，2025，§2–3、附录 A）](https://arxiv.org/abs/2506.10947)在 DeepScaleR 数据上用 GRPO 训练 Qwen2.5-Math-7B，将正确性奖励替换为随机 0/1 奖励后，MATH-500 的单次作答准确率仍提高了 21.4 个百分点，使用真实答案奖励时则提高 29.1 个百分点。作者测试的 Llama3、OLMo2 模型通常没有同样的收益。这是特定模型和训练设置下的分析实验，不是随机奖励普遍有效的证据，也不是奖励投机的直接证明。

这组结果还需要连同实验设置一起读：每题采样 16 次，训练温度为 1，不加 KL 散度（Kullback–Leibler divergence）惩罚或熵（entropy）损失，使用 8 张 A100。MATH-500 评估采用贪心解码；上述增幅按论文对训练曲线末点做十步平滑的口径报告。

数学题也一样：最终答案匹配，不足以证明中间每一步都成立。模型可能蒙对，或者过程有错却碰巧得到正确结果。是否需要检查过程，取决于你到底要求一个正确答案，还是一份可依赖的论证。

这不表示任何模型都会找到所有漏洞。更准确地说，奖励提供了优化方向；模型能否利用漏洞，还取决于它的能力、采样和训练过程。排查时，不要只看奖励是否升高，要看独立检查是否也支持“任务做得更好了”。

## 一个排序检查，少验了哪一件事？ {#reward-entropy-example}

输入是 `[3, 1, 1]`。如果验证器只检查输出是否从小到大，下面 3 个结果都会通过：

| 输出 | 非递减？ | 保留了所有原元素及次数？ |
| --- | --- | --- |
| `[1, 1, 3]` | 是 | 是 |
| `[1, 3]` | 是 | 否，少了一个 1 |
| `[]` | 是，没有相邻逆序 | 否，元素全没了 |

排序不仅要求有序，还要求输出是输入的一个排列：每个元素都保留，出现次数也不变。下面只用整数列表演示：

```python
from collections import Counter

def verifies_sort(original, candidate):
    ordered = all(
        left <= right
        for left, right in zip(candidate, candidate[1:])
    )
    return ordered and Counter(original) == Counter(candidate)
```

这段代码是检查**一对输入输出**的教学函数，不验证所有可能输入，也不负责安全执行未知程序。实际代码评估还要考虑输入类型、是否修改输入、异常、超时和隔离；这些约定要按任务写清楚。

现在假设模型在 `[1, 3]` 和 `[]` 之间等概率选择。用熵衡量这道固定题目上输出分布的不确定性，得到 $\log2$，但两个输出都没完成任务。它也可以总返回正确的 `[1, 1, 3]`，熵为 0，却完全满足这道题。**奖励是否有漏洞、输出熵是否下降，需要分别检查。** [熵的算例](alignment-tax.md#entropy-versus-hacking)把这个区别列成了对照表。

<details markdown="1">
<summary>怎样检查验证器，而不只是检查模型？</summary>

先准备一些人能直接判断的故意错误输出：漏元素、重复元素、顺序颠倒、空结果。它们不该因为格式像正确答案就得满分。再加入正确的边界情况，例如空输入对应空输出、重复值和负数。

把测试分成用于训练评分的一组，以及没有参与训练或筛选的保留组。留出测试并不保证它完全独立：两组测试若使用同源模板或同一个有缺陷的解析器，仍可能一起出错。要针对不同错误机制补充检查，并抽样人工复核。修改评分规则后，还应复测此前保存的模型版本，避免把评分变化误当成模型进步。

</details>

## 二元奖励何时缺少组内信号 {#_5}

回到排序函数：同一个题目采样 4 份实现，测试结果是 `[0, 0, 0, 0]`。如果用结果奖励减去组均值来计算优势值（advantage），4 个值都是 0；这一项无法区分该提高哪个回答的生成概率。`[0, 1, 0, 0]` 才给出了组内差异。若还要除以组内标准差，则必须处理标准差为 0 的情况，例如在分母加一个小正数，不能直接计算 $0/0$。

这里说的是结果奖励对应的策略梯度项。若还有用于约束策略偏离参考模型的 KL 惩罚、调节输出多样性的熵目标或其他辅助目标，参数仍可能更新。程序奖励也不必只能是 0/1：按测试通过比例评分，可以区分部分完成的情况，但也改变了目标，可能鼓励只做容易通过的部分。

题目难度和采样预算因此很重要。先统计多少组全对或全错，再判断是需要更合适的题目、更强的起点，还是更多尝试。

全同分组有多常见，可以用 [DAPO 动态采样方法中的混合组概率](dapo.md#dynamic-sampling)估算。固定一道题，假设各次采样独立、成功概率均为 $p$，每组有 $G$ 个回答。全对的概率是 $p^G$，全错的概率是 $(1-p)^G$，所以全同分的概率为 $p^G+(1-p)^G$，与混合组概率之和为 1。$G=4$ 时，$p=0.5$ 只有 12.5% 的组全同分，$p=0.1$ 或 $0.9$ 时都升到 65.62%：太难和太容易都可能让组内信号很弱。

这是独立同分布的算例；实际题目难度不同、采样相关时，应直接记录每题各组的结果，不能用整个数据集的平均成功率 $p$ 硬套。

像 DAPO 那样过滤全同分组，能提高参与更新的样本中有组内差异的比例，但需要额外采样，也会改变进入更新的题目分布。它不能凭空创造困难题的正确解法。与[筛选后做监督微调](rejection-sampling.md#prompt-selection)一样，要同时看保留量和题目覆盖。

## 结果奖励还是过程奖励 {#_6}

结果奖励（outcome reward）只检查最终结果，容易接进训练，却无法定位哪一步出错。过程奖励（process reward）可以给出更细的反馈，前提是中间步骤确实能被可靠判断。人工标注成本高，模型标注可能误判，形式化证明检查则需要合适的表示和工具。

不必把二者当成只能选一个。例如最终结果由测试判定，过程信号帮助搜索；但要单独验证增加过程信号后，是否真的在相同预算下更容易做对，而不是只让过程分更高。

推理时怎样用结果奖励模型和过程奖励模型挑答案、在中间步骤上搜索，见前沿草稿[测试时计算：多采样、投票与验证器](../11-frontier/test-time-compute/parallel-and-verify.md)。读论文时也要看收益发生在选答案还是训练模型这一步。[Let's Verify Step by Step，§2.1](https://arxiv.org/html/2305.20050v1#S2.SS1)固定生成模型，比较奖励模型从多个候选中选答案的能力，并没有用强化学习更新生成模型。因此，“过程评分更会选答案”不能直接改写成“用过程奖励训练出的策略更强”；后者需要另做训练与评估。

## 可验证性是个连续谱，不是二分 {#_7}

更实用的分类是“到底验证了哪一层”：

| 检查 | 能说明什么 | 不能单独说明什么 |
| --- | --- | --- |
| 编译通过 | 满足编译器检查的语法和类型要求 | 程序完成了任务 |
| 通过单元测试 | 在这些输入上符合预期 | 所有输入都正确 |
| 数学答案匹配 | 最终结果符合给定答案与解析规则 | 中间推理有效 |
| 引用确实存在 | 来源可找到 | 来源支持这条结论 |
| 人或模型按标准评估 | 在给定证据和标准下的判断 | 不存在偏差或分歧 |

一个任务可以同时用几种检查。例如生成报告时，程序核对数字和链接，人再判断论证是否合理。让每个判断用合适的证据，比把所有要求都压成一个分数更容易排查问题。

## 设计可验证奖励时检查什么 {#_8}

1. 哪些故意错误的答案仍能得满分？能否加入针对性的反例测试？
2. 如果奖励是二元的，每批训练数据中有多少比例的组是全对或全错？
3. 我验的是结果还是过程？验结果的话，蒙对的比例有多高？
4. 这个任务真的“不可验证”吗，还是没有拆开检查？其中哪一部分其实可以验证？
5. 若增加模型评判，独立检查能否发现它偏爱的错误？

## 快速学习：可验证奖励换掉了什么 {#_2}

<details class="interview" markdown="1">
<summary>复习时，用排序检查讲清楚奖励的边界</summary>

**先记住**：测试能明确检查某些性质，不代表整个任务已经验证完。高奖励、低熵和高质量不是同一个指标。

**面试回答**

> 我会先说清验证器检查什么，再主动构造会通过检查、却不满足任务的反例。比如排序只检查有序还不够，必须保留元素及次数。之后用保留测试和固定采样预算评估模型，而不是只报训练奖励。

<details markdown="1">
<summary><b>深挖</b>：结果奖励与过程奖励怎样取舍？</summary>

结果奖励是否可靠，取决于任务规格和验证器覆盖，不是天然“偏差小”。过程奖励提供更细反馈，但也增加要验证的判断。二者都需要独立质量检查。
