## 奖励从模型变成可检查规则 {#_3}

让模型写一个排序函数，可以请另一个模型判断“写得好不好”，也可以把结果拿去跑测试。后者把一部分判断变成了可重复检查的程序。

如果测试只包含 `[3, 1, 2]`，一直返回 `[1, 2, 3]` 也能过。换成空列表、重复元素或负数，这个实现马上露馅。可验证奖励的价值在于检查明确、方便复现，不在于它天然没有漏洞。

## 换掉了什么 {#_4}

回顾 [RLHF 的四个模型](rlhf/three-stages.md)：Policy、Critic、Reward、Reference。可验证奖励删掉的是 **Reward Model**——那个用[偏好数据](where-preferences-come-from.md)拟合出来的网络。

$$r(x,y) = \text{verify}(y) \in \{0, 1\}$$

一个确定性函数取代了一个学出来的函数。

## 为什么它能收窄 reward hacking {#reward-hacking}

用测试替换 RM 后，不再需要让一个模型从语言外观猜代码是否正确。测试检查的性质更明确，失败也更容易复现。这能减少一类奖励模型泛化错误。

但“奖励是离散的、不可微”并不能阻止模型钻空子。Policy gradient 根据采样结果的分数调整概率，并不需要把梯度穿过测试程序。能通过不完整测试的错误实现，仍可能被逐渐强化。

## 但 reward hacking 只是换了地方 {#reward-hacking_1}

这一节是重点，因为"用了 RLVR 就没有 reward hacking 了"是个危险的简化。

**验证器本身可能有洞。** 如果奖励是"通过测试"，而测试覆盖不全，那么模型学到的是**通过这些测试**，不是**写对代码**。它会：

- 针对测试用例硬编码返回值；
- 捕获所有异常让程序不崩溃，从而通过"不报错"这类检查；
- 找到测试框架本身的漏洞。

数学侧同理：只验最终答案的话，模型可以通过**猜**、通过写一堆看起来像推理但和答案无关的东西然后蒙对来拿分。**过程是错的，奖励是满的。**

一般化的说法是：**你验证的东西，就是模型会去优化的东西——不多也不少。** 这和奖励模型时代的教训是同一条，只是这次那个"错误的目标"是你自己写下来的，因此至少是可读、可审计、可修的。

## 二元奖励带来的新问题：信号太稀疏 {#_5}

回到排序函数：同一个题目采样 4 份实现，测试结果是 `[0, 0, 0, 0]`。如果训练只用减去组均值的结果奖励，4 个 advantage 都是 0；这一项无法区分谁更值得提高概率。`[0, 1, 0, 0]` 才给出了组内差异。

这里说的是结果奖励对应的策略梯度项。若还有 KL、熵或其他辅助目标，参数仍可能更新。程序奖励也不必只能是 0/1：测试通过比例可以更密，但也改变了目标，可能鼓励只做容易通过的部分。

题目难度和采样预算因此很重要。先统计多少组全对或全错，再判断是需要更合适的题目、更强的起点，还是更多尝试。

## 结果奖励还是过程奖励 {#_6}

只验最终答案（结果奖励）便宜，但会奖励"蒙对"。验中间步骤（过程奖励）信号密得多，但**中间步骤谁来标**——如果要人标，你就又回到了偏好数据那套成本和噪声里。

现在常见的折中是用模型来生成或校验过程标签，但那等于**又引入了一个学出来的评判者**，也就把那个可被攀爬的表面请了回来。这个取舍没有免费解。

## 可验证性是个连续谱，不是二分 {#_7}

更实用的分类是“到底验证了哪一层”：

| 检查 | 能说明什么 | 不能单独说明什么 |
| --- | --- | --- |
| 编译通过 | 满足编译器检查的语法和类型要求 | 程序完成了任务 |
| 通过单元测试 | 在这些输入上符合预期 | 所有输入都正确 |
| 数学答案匹配 | 最终结果符合给定答案与解析规则 | 中间推理有效 |
| 引用确实存在 | 来源可找到 | 来源支持这条结论 |
| 人或模型按标准评估 | 在给定证据和标准下的判断 | 不存在偏差或分歧 |

一个任务可以同时用几种检查。例如生成报告时，程序核对数字和链接，人再判断论证是否合理。让每个判断用合适的证据，比把所有要求都压成一个分数更容易排查问题。

## 设计可验证奖励时检查什么 {#_8}

1. 我的验证器有多少洞？我有没有试着**故意**去骗它一次？
2. 如果奖励是二元的，我的 batch 里有多少比例的组是全对或全错？
3. 我验的是结果还是过程？验结果的话，蒙对的比例有多高？
4. 我这个任务真的"不可验证"吗，还是我没拆开？哪一部分其实是可验的？
5. 如果我引入了模型评判者，那个可被攀爬的表面是不是又回来了？

## 快速学习：可验证奖励换掉了什么 {#_2}

<details class="interview" markdown="1">
<summary>Verifier、稀疏奖励与 reward hacking 的新位置</summary>

**快速记忆**：能写 checker 时，用程序验证结果比让 RM 猜质量更可靠；但模型仍可能 exploit checker、环境或题目分布。

**面试回答**

> Verifiable reward 把学出来的 proxy 替换为可重复检查的规则，例如单元测试、数学答案或环境终态。它减少 RM misgeneralization，却常产生稀疏二元信号，并把 reward hacking 转移到 verifier specification、sandbox 和数据生成流程。

<details markdown="1">
<summary><b>深挖</b>：Outcome reward 与 process reward 怎样取舍？</summary>

Outcome reward 偏差小但 credit assignment 稀疏；process reward 更密集，却需要可靠地验证中间步骤，否则把人为偏见写进轨迹。实践中可用结果 verifier 作为硬终态，再用谨慎校准的过程信号改善搜索效率。
