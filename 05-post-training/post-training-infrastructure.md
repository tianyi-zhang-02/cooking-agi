## 先跟着一条回答走一遍 {#_2}

给模型一道乘法题，它调用计算器，读到结果，再写出答案。到这里，我们有了一次运行记录，却还不一定有一条能直接用于训练的数据：哪些词元（token）是模型选的？生成时用的哪版权重？它是真的完成了，还是被长度限制叫停了？

这些信息不是可有可无的调试日志。丢了它们，可能连损失应该算在哪些位置都说不清。下面先讲轨迹采集（rollout）要留下什么，再沿着生成、评分、更新的依赖关系看吞吐，最后检查对数概率（log-prob）和上下文是否一致。算例均为教学假设，不是某个框架的实测性能。

## Rollout 不等于一条完整答案 {#_3}

**Rollout 是让策略实际运行，收集动作、观察和结果的过程。** 可以一次跑一个任务，也可以批量跑；可以收集完整任务，也可以只收集一段。这个词本身既不保证使用最新策略，也不要求一定有奖励模型。

| 名称 | 在计算器任务里指什么 | 容易混淆的地方 |
| --- | --- | --- |
| 一段生成（completion） | 一次模型调用生成的 token 序列 | 工具调用也可能是一段生成，不一定是最终答案 |
| 助手回合（assistant turn） | 助手的一次发言或工具请求 | 具体边界取决于对话模板与运行协议 |
| 完整任务（episode） | 从题目到成功、失败或定义好的终点 | 可能包含多次模型调用和环境返回 |
| 轨迹片段（fragment） | 收集器暂时截下的一段过程 | 不一定走到了任务终点 |

模型生成了结束标记，可能只是这一轮发言结束；工具还没返回，整个任务就还没有完成。反过来，若任务本来只要求一条回答，一段生成也可以就是整个任务。先认清这里的边界，才知道该在何时评分、哪些动作属于同一次训练记录。

### 一条能用于训练的记录 {#rollout-record}

把这次计算器交互拆成下面几段。长度只是虚构数字，不代表实际分词器的切分：

| 片段 | token 数 | 是否作为策略动作计算损失 | 原因 |
| --- | ---: | --- | --- |
| 用户题目 | 6 | 否 | 是输入条件 |
| 助手工具请求 | 4 | 是，按该任务约定 | 是模型实际生成的选择 |
| 计算器结果 | 3 | 否 | 来自环境，不是策略采样 |
| 助手最终回答 | 5 | 是 | 是模型生成的答案 |
| 填充位置 | 2 | 否 | 只是对齐批次 |

输入共有 20 个位置，但有效动作只有 9 个。若按有效动作平均策略损失，分母就应是 9，不能随手写成 20。工具结果虽然不直接产生策略损失，仍会影响后续动作；“不算它的损失”不等于“从上下文里删掉”。角色 / 控制标记是否为采样动作，要按真实生成协议决定，不能仅凭文本长相。

记录至少包含下列几类信息，字段名随实现而定：

| 信息 | 为什么留它 |
| --- | --- |
| 输入 / 任务标识、token IDs、角色边界、有效动作掩码（mask） | 对齐 logits、动作和后续回放 |
| 行为策略（behavior policy）版本、采样参数、动作对数概率 | 知道这条数据怎样被采出来 |
| 停止原因、最终观察、工具状态与错误 | 区分任务终止、收集截断和运行失败 |
| 奖励来源 / 版本、评分状态 | 未评分不是零分；工具超时也不自动等于模型答错 |
| 按需保存的旧策略 / 参考策略对数概率、价值、回报 / 优势 | 明确由哪个模型、在哪一步算出 |

奖励可以来自测试、环境、人工或学习出的评分模型。参考策略的对数概率、价值、优势不一定都在生成时计算，甚至不一定都需要；不要为了凑一张大表而混淆算法角色。PPO 的轨迹缓冲区通常只服务一轮有限的多次更新，不等于历史经验可以无限重放。[PPO 原论文](https://arxiv.org/abs/1707.06347)讨论的是采样与多轮小批量更新交替进行。

<details markdown="1">
<summary>小检查：20 个位置，为什么只平均 9 个？</summary>

下面已经按“被预测的 token”对齐，不再演示 logits 的移位。数值是任意的逐位置教学损失。真实实现还要核对下一 token 的移位与采样协议。

```python
def action_mean(values, mask):
    if len(values) != len(mask) or any(flag not in (0, 1) for flag in mask):
        raise ValueError("aligned values and binary mask required")
    count = sum(mask)
    if count == 0:
        raise ValueError("no policy actions")
    return sum(value for value, flag in zip(values, mask) if flag) / count

mask = [0] * 6 + [1] * 4 + [0] * 3 + [1] * 5 + [0] * 2
values = [99.0] * 6 + [2.0] * 4 + [99.0] * 3 + [4.0] * 5 + [99.0] * 2
assert len(mask) == 20 and sum(mask) == 9
assert abs(action_mean(values, mask) - 28 / 9) < 1e-12
```

</details>

### 到了终点，还是只是采样时间用完了？ {#rollout-boundaries}

动作位置对齐后，还要看记录为什么结束。假设当前一步奖励为 0.2，下一状态估值为 0.8，折扣 $\gamma=0.9$。计算一步时序差分目标（TD target）时：

- 任务真的终止：没有后续回报，目标值为 0.2。
- 只是外部收集时间到了，任务本可继续：保留自举估计，目标值为 `0.2 + 0.9 × 0.8 = 0.92`。

这不是让你一律给长度截断补一个价值估计。若任务定义为“最多 10 步，没完成就失败”，预算耗尽本身就是终点；如果只是收集器每 10 步暂停一次，就不是同一种情况。[Gymnasium 的时间限制说明](https://gymnasium.farama.org/tutorials/gymnasium_basics/handling_time_limits/)明确区分终止与截断；有限时域任务还需要让观察包含剩余时间等必要信息。

自举估计要使用被截断轨迹的最后状态，不能误用环境重置后新任务的第一帧。若做广义优势估计（GAE），暂停收集的边界通常还要截断优势递推，不把下一个任务的误差串过来；**自举掩码和递推边界掩码不一定相同**。没有价值模型的方法，则按自己的截断和奖励约定处理，不必硬加一个价值字段。

## 采样慢，先分清时间花在哪里 {#rl}

一批数据可能依次经历生成、工具等待、评分、训练、权重同步。只盯 GPU 利用率，很容易把“GPU 在等工具”误判成“模型太小”。按 NVML 的定义，`nvidia-smi` 里的利用率只是采样周期里有计算内核在跑的时间比例，不说明算力用了多少，见[性能：roofline、算术强度与 MFU](../12-infra/performance.md)。要判断哪些等待能省掉，先看数据依赖，而不是先加机器。

### 同一批数据，哪些步骤必须等？ {#generation-to-update}

继续看计算器任务：最终回答依赖工具返回，评分又依赖相应的回答或轨迹。对于一批准备拿来更新的数据，可以按下面的关系逐项核对；这不是要求所有工作都放在一个进程里串行执行。

| 工作 | 需要先有什么 | 交给后续步骤的是什么 |
| --- | --- | --- |
| 生成与工具交互 | 输入上下文、实际加载的行为策略及采样设置 | 动作、观察、生成版本和停止原因 |
| 评分与训练前准备 | 评分所需的回答或轨迹；各项统计量所需的模型与输入 | 奖励、评分状态，以及算法所需的旧策略 / 参考策略对数概率、价值等 |
| 计算目标并更新 | 已就绪的训练记录与所需统计量；例如优势计算依赖相应奖励及所需价值 | 按动作掩码计算损失，完成反向传播和优化器更新后的权重 |
| 发布权重 | 已完成的更新，以及生成端的加载与版本确认 | 后续采样可以实际使用的新版本 |

评分、参考策略计算和价值计算，在各自输入就绪后可以有并行机会；但不能把“尚未评分”当成零奖励送进更新。训练端完成更新，也不代表生成端已经加载新权重。以 PPO 为例，可对照[原论文第 5 节的 Algorithm 1](https://arxiv.org/pdf/1707.06347#page=5)看采样、优势估计、更新与策略交接的顺序；它并不要求所有方法都配齐参考模型和价值模型。

### 不同批次，哪些时间可以重叠？ {#pipeline-overlap}

异步系统主要是把不同批次的工作交错起来，不是取消同一条记录的数据依赖。若要求每批都使用上一批更新并发布后的权重，就不能同时让下一批提前生成；允许提前生成，才需要进一步管理策略版本滞后。

用一组假设时间算账：采样 30 秒，评分 10 秒，训练 20 秒，同步 5 秒。完全串行需要 65 秒。如果前三段有独立资源、允许跨批次提前生成并理想重叠，而每批同步的 5 秒不能与其他工作重叠，稳态间隔下界才是 `max(30, 10, 20) + 5 = 35` 秒，约 1.86×。这里的 35 秒是理想稳态下相邻批次完成的间隔下界，不是单批从生成到更新完成的延迟。这也不是“异步必然快一倍”：首批仍要经过完整流程，资源争用、长尾任务和网络都会增加时间。

| 方式 | 省心在哪里 | 需要付出的代价 |
| --- | --- | --- |
| 同步采样，再更新 | 版本和批次边界清楚，容易排查；生成和训练可以轮流使用同一批 GPU | 各阶段可能互相等待 |
| 限制队列长度的异步 | 能重叠部分生成与训练 | 需要处理策略延迟、丢弃规则和回压 |
| 深队列、持续采样 | 容纳突发数据和慢任务 | 可能更旧、更占内存，不保证有效更新更快 |

要同时记录采样 tokens/s、真正参与损失的 tokens/s、队列等待分位数、版本落后程度、超时 / 丢弃比例，以及相同实际运行时间下的任务质量。更高吞吐若主要来自收集无效回答，就没有省到学习成本。异步方法的目标差异见[异步策略学习](async-policy-learning.md)。

## 同一份权重，log-prob 也可能对不上 {#_4}

版本记录能告诉我们数据有多旧，却不能单独说明它的概率是否与训练端一致。还要分清三种分布：模型原始分布、温度 / top-p 等处理后的采样分布、训练框架重算出的分布。它们可能相同，也可能不同。引擎返回的字段叫 `logprob`，不代表已经告诉你是哪一种。

例如原始概率为 `[0.8, 0.2]`。用温度 2 采样，概率变成 `[2/3, 1/3]`。若新模型给第二项概率 0.25，相对实际行为分布的比率是 `0.25 / (1/3) = 0.75`；若错用原始 0.2 作分母，就变成 1.25，连增减方向都反了。top-p 截掉某些动作后，还会引入支持集问题，不能假装普通重要性采样能恢复从来没采过的部分。

<!-- widget:step-behavior-ratio -->

若选择以实际行为策略 $b$ 为基准，一个动作的比率为：

$$
r_t(\theta)=\frac{\pi_\theta(a_t\mid s_t)}{b(a_t\mid s_t)}.
$$

也有实现用训练端重算的旧策略作为 PPO 比率的基准，再另外校正采样策略与旧策略的差异。**分母不是永远来自推理引擎，也不是永远能由训练端替换。** 要按目标和实现看这几个分布怎样对应。[verl 的采样校正文档](https://verl.readthedocs.io/en/latest/algo/rollout_corr.html)区分了这两类设计；此处核对的是 2026-09-23 更新的文档，不保证未来配置名称不变。

这份文档背后有几篇一手资料，值得直接读。博客 [“Your Efficient RL Framework Secretly Brings You Off-Policy RL Training”](https://fengyao.notion.site/off-policy-rl) 指出，推理引擎（如 vLLM）和训练框架给同一个 token 算出的概率并不相同。因此，即使在线收集新样本，原本希望保持 on-policy 的训练也可能出现采样策略与训练策略不一致的偏差。它的修正是把训练端与推理端的概率比截断到一个区间内，再乘到梯度上，叫截断重要性采样（truncated importance sampling, TIS）。

[“When Speed Kills Stability”（Liu 等，2025）](https://richardli.xyz/rl-collapse)把这种不一致和 RL 训练崩溃联系起来，并比较 token 级与序列级的修正。[Ring-1T 报告（Ling Team，2025）](https://arxiv.org/abs/2510.18855)里的 IcePop 则对差异过大的 token 做 mask 和裁剪。

框架也在跟进：截至 2026-10，[TRL v1.16.0](https://huggingface.co/docs/trl/v1.16.0/en/grpo_trainer) 用 vLLM 生成时默认打开这类修正（`vllm_importance_sampling_correction=True`；配置签名里的默认模式是按整条序列 mask 的 `sequence_mask`，上限 `vllm_importance_sampling_clip_max=3.0`）。默认打开不等于问题已经解决：先查清差异从哪来，再决定截断还是丢弃。

这里也核对了同版本的[配置字段定义](https://github.com/huggingface/trl/blob/v1.16.0/trl/trainer/grpo_config.py)：实际默认值是 `sequence_mask`，但该文件的模式说明仍把 `token_truncate` 标成默认。阅读时应以字段定义为准，不把两种模式混为一谈。

统一采样语义后，再查计算内核、精度、模板、位置、掩码等差异。用同一批 token、同一份权重在两侧评分，按有效动作统计差值的分位数、极端值，并按长度分组检查，不要求所有硬件都逐位一致。比率偏离大也不一定全因数据旧了：对齐错误和数值差异同样可能造成。

<details markdown="1">
<summary>为什么只看平均差值不够？</summary>

两个动作的对数概率差分别是 +0.7 和 −0.7，平均恰好为 0。取指数后，比率却约为 2.01 和 0.50，平均也不再是 1。这是指数非线性的简单例子，不是实际误差分布。

还要分清监控对象：原始比率超出裁剪区间，不等于梯度一定被裁掉。PPO 实际采用哪个分支，与优势的正负有关。详情见 [PPO clipping](rlhf/ppo-clipping.md)；不要只凭一个裁剪比例指标就断言训练已经失效。

</details>

## 上下文删掉什么，训练就看不到什么 {#_5}

概率对齐之外，还要核对模型当时究竟看见了什么。继续用工具任务：用户最早说“不要改动原文件”，几轮之后，为了腾出窗口，系统把这句话删了。最终模型改动了文件，问题就不只是奖励给得不好：它做决定时根本没看到约束。多轮智能体训练里，截断和压缩怎样影响记分与损失，见前沿草稿里的[回合变长以后](../11-frontier/agentic-rl/credit-and-training.md)一节。

| 处理方式 | 能省下什么 | 要验证什么 |
| --- | --- | --- |
| 保留最近若干轮 | 实现简单、长度可控 | 目标与早期约束是否被挤掉 |
| 固定保留目标，裁剪重复工具输出 | 少一次摘要模型调用 | 裁剪规则是否误删证据 |
| 摘要旧历史，必要时检索原记录 | 可保留更长任务的主要信息 | 摘要错误、遗漏和检索失败 |

这些做法同时影响任务完成率、答案质量和延迟，不只是“让上下文装得下”。更换压缩策略改变了策略看到的观察，不一定改变底层环境的转移规则；丢掉必要历史还可能让观察不再满足 Markov 条件。把模板、摘要器 / 检索器版本、原始工具记录和外部状态一起管理，才能比较实验并恢复任务。

## 先跑通一小批，再扩大规模 {#_6}

不必一开始就搭最复杂的异步系统。先固定一小批任务，追踪它们从采样到损失的每一步：动作数能对上，终止原因能解释，奖励能复核，生成与更新版本能追溯，再去优化等待时间。这里没有“算法一定比工程次要”的排序；需要排除的，是代码实际上没有执行你以为的那个目标。

这些改动也不是都不改变目标函数。更换截断奖励、数据筛选或采样处理，可能改变训练分布、估计量甚至任务定义。把变动记录下来，比笼统地叫它“提速优化”更有用。

## 放大训练前，我会检查这些 {#_7}

1. 从一条原始记录，能重新对齐 token、角色、策略动作掩码和下一 token 的 logits 吗？
2. 未评分、工具失败、任务失败、长度截断，是否被悄悄合成了同一个零分？
3. 旧策略、当前策略、参考策略与实际行为分布分别是什么？采样参数是否留档？
4. 同步改成异步后，采样吞吐、数据年龄和等时间质量是否一起报告？
5. 恢复时除了模型权重，队列、采样器、工具与上下文状态是否也有明确处理？生成端实际加载了哪一版，能核对吗？

## 如果只记住一件事 {#systems-problem}

Rollout 不只是“生成一点训练数据”。它要留下足够的信息，让训练知道模型在什么条件下作了哪些选择。先让这条记录能够正确地接入评分与更新，再看怎样跑得更快。
