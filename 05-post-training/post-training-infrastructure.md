# 后训练的基础设施：采样、数值、上下文

**中文** · [English](post-training-infrastructure.en.md)

> 阅读时间：约 7 分钟 · 类型：教学 · 最近审阅：2026-08

## 先用一句话讲清楚

关于后训练的公开讨论几乎都在算法上——用 PPO 还是 GRPO，要不要 Critic。但真正卡住一次后训练的，常常是另外两个问题：**一小时能采到多少经验**，以及**训练侧和推理侧算出来的是不是同一个数**。这两件事都不出现在任何损失函数里。

## 为什么这一层被忽略

因为它不出论文。换一个损失函数可以写成一个公式、画一条曲线、起一个名字；把 rollout 吞吐提高三倍写不成公式。

但从投入产出看，顺序常常是反的：**算法换代带来的提升是百分之几十，而采样吞吐翻倍等于在同样的时间里把整个实验做两遍。**

## 一、采样吞吐：RL 真正的成本中心

监督学习的数据是现成的。**RL 的数据要现场生成**，而且必须由当前策略生成——这是 on-policy 的定义。

于是每一步训练前都要先跑一遍推理。任务越长，这个比例越夸张：

- 一次单轮对话的采样，几百毫秒
- 一个多步 agent 任务，几分钟——中间还夹着工具调用、环境响应、等待

**同步实现里，训练进程在整个采样期间是闲着的。** 长程任务上，GPU 利用率可以低到让人不忍心看。

异步化是标准解法：让一批 actor 持续产出经验塞进队列，训练进程从队列取。吞吐立刻上去了。

**但代价不是零**，而且代价的名字我们已经见过：**队列里的经验来自更旧的策略。** 你为了吞吐，把 on-policy 往 off-policy 推了一点。

这就是那个真实的取舍：

| 异步程度 | 吞吐 | 经验新鲜度 | 后果 |
| --- | --- | --- | --- |
| 完全同步 | 最低 | 严格 on-policy | GPU 大量空转 |
| 轻度异步 | 高 | 落后一两步 | 重要性采样能修正 |
| 重度异步 | 最高 | 落后很多步 | 比率方差爆炸，裁剪频繁触发，等于在丢弃梯度 |

**判据不是"越异步越好"，是"重要性采样比率的分布还正常吗"。** 比率大量堆在裁剪边界上，说明你采的经验对当前策略已经太旧了——此时提高的吞吐并没有变成学习。

## 二、数值一致：一道不报错的裂缝

采样跑在推理引擎上，训练跑在训练框架里。两边的 kernel 实现、精度、算子融合方式都不同，所以**同一段文本、同一份权重，两边算出来的 logprob 可以对不上**。

而重要性采样比率的分子和分母，正好一边一个：

$$r_t(\theta) = \frac{\pi_\theta(a_t \mid s_t)}{\pi_{\theta_{\text{old}}}(a_t \mid s_t)}$$

分母是**推理引擎报的**，分子是**训练框架算的**。两边有系统性偏差时，这个比率里就混进了一个与策略变化无关的因子。

后果：你以为在做 on-policy，实际上采样策略和被优化的策略之间有一道你没建模的裂缝。**裁剪照常工作，但它裁的是一个被污染的比率。**

**而这件事不会报错。** loss 正常下降、指标正常波动，只是每一步的更新方向都带一点系统性的偏。

自检很直接：拿同一批文本，在两侧各算一次 logprob，看差异的分布。

```
diff = logp_train - logp_rollout
# 关心的不是均值（均值可以为 0 而分布很宽），
# 是分位数和最大值。长尾意味着某些 token 的比率被严重扭曲。
```

有一个真实系统把这个差异压到 $10^{-7}$ 量级之后取得了显著提升（见[同一个基座能走多远](same-base-different-posttraining.md)）。收益不体现在任何公式里，体现在**之前所有的更新终于名副其实**。

## 三、上下文管理：让长任务能够完成

多步 agent 任务的上下文是单调增长的：每一次工具调用、每一段环境返回，都往里加。跑够久必然撑爆。

撑爆之后的默认行为是截断，而截断掉的往往是**最早的那部分**——也就是任务目标和初始约束。模型于是在任务后半程忘记自己在干什么。

压缩（把历史摘要化、把冗余的工具输出折叠）解决的是**能不能完成**，不是**完成得多好**。这个区分很重要：它不是一个提升质量的技巧，它是长程任务的准入条件。

一个容易忽略的连带影响：**压缩改变了状态。** 同一个任务，压缩策略变了，模型看到的上下文就不一样，于是它是一个不同的 MDP。**压缩策略必须和模型版本一起版本化**，否则你会拿两个不同环境下的结果做比较。

## 三者的共同点

它们都**不改变目标函数**，但都改变你能对目标函数做什么：

- 采样吞吐决定**你能在给定时间里走多少步**
- 数值一致决定**每一步走的方向对不对**
- 上下文管理决定**这个任务能不能被走完**

一个非常实际的推论：**当你的后训练效果不好时，先排查这三样，再考虑换算法。** 顺序反过来的代价是——你会用一个更复杂的算法，去修一个不是算法造成的问题，并且大概率修不好，然后得出"这个算法没用"的错误结论。

## 落到检查清单

1. 我的 GPU 在采样期间在干什么？我量过训练/采样的时间比例吗？
2. 重要性采样比率的分布长什么样？有多大比例卡在裁剪边界上？
3. 训练侧和推理侧的 logprob 差异有多大？我量过分位数，还是只看了均值？
4. 长任务的上下文是怎么被截断或压缩的？截掉的是不是任务目标？
5. 我的压缩策略版本化了吗？还是它悄悄变过，而我在比较两个不同的环境？
