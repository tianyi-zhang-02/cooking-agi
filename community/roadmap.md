## 现在：更快的搜索和页面 {#now}

读者来这里，多半是想尽快查到一个概念、一段推导或一道题。所以先把「找」和「打开」做好：

- **搜得更准**：英文词从词首开始匹配，不会因为 exploration 里有 lora 就算命中；`kv-cache` 和 `kv cache` 结果一样；不专讲这个词的笔记，结果会直接跳到匹配的小节。
- **搜得更快**：索引按语言拆开，去掉重复的内容。手机上第一次搜索从约 3.7 秒降到约 1.8 秒，手指一碰到搜索按钮就开始加载。
- **页面更轻**：交互实验和公式渲染只在用到它们的页面加载。文件按内容加版本号，网站定时重建时，内容没变，读者就不用重新下载。

这一批改动在 [#128](https://github.com/tianyi-zhang-02/cooking-agi/pull/128)。还没做好的：拼错的词（比如 atention）还搜不到，有些排序还要再调。

## 接下来：按顺序，一件一件做 {#next}

1. **给更多笔记补分步动画。** 有些机制看图比读字快，比如 prefill 和 decode 各算了哪些位置。一次只做一张：先给静态草图，确认讲对了，再做成可以一步步播放的图。例子见 [Decoder-only](../00-foundations/core/decoder-only.md) 里的 prefill / decode。
2. **远程 MCP 服务。** 网站已经有一份只读的数据接口（`/api/v1/`），面试练习 skill 就从这里读笔记和题目。MCP 服务读同一份数据，让 Claude、ChatGPT、Cursor 这些助手可以直接查笔记、按笔记出题，不用另存一份内容。
3. **按重要机制整理题库。** 题目现在散在各篇笔记里，[考前速查](../interview/questions.md)按板块把它们列在一起。接下来按机制归类，比如注意力、KV cache、归一化、PPO / DPO、解码，每道题都链接到讲清楚它的那一小节。

**面试准备版（v1.0）不做了。** 已有的面试笔记、按计划学习、收藏和阅读记录照常可用，但不再继续加面试准备的专门功能。账号、云同步、连续打卡和学习排行榜也不在计划里。

## 后续方向：先从一个小项目开始 {#future}

下面是想扩展的方向，**还不是完整课程，也没有安排固定负责人或上线时间**。目前的笔记偏 ML / LLM；这些领域更需要真正做过的人来写、来挑错。

| 方向 | 可以先写什么 | 第一个项目可以多小 |
| --- | --- | --- |
| 计算机视觉（CV） | 图像输入、卷积与 ViT、分类／检测／分割的差别，数据和评估怎么选 | 固定一个公开数据子集，做 baseline，看看错误集中在哪里 |
| 自动驾驶 | 感知、预测、规划和控制分别做什么，模块之间传什么信息 | 在公开数据或仿真里拆解一个环节，不把离线分数当成道路安全证明 |
| Jetson 与边缘部署 | 从模型导出到设备推理，延迟、内存、功耗怎样取舍 | 部署一个小视觉模型，写明设备、软件版本和测量方法；没有设备也能先读懂流程 |
| 物理仿真（Physical simulation） | 状态、动作、时间步、接触和传感器噪声；仿真有哪些简化 | 做一个简单控制任务，改一个假设，观察结果为什么变了 |
| 机器人 | 坐标系、运动学、控制、模仿学习与 RL，怎样连成完整系统 | 从仿真的机械臂或移动机器人开始，说明哪些结论不能直接搬到真机 |

这些方向不是五套互不相干的教材。数据、评估、优化、系统和部署能共用的部分，继续链接已有笔记。我们尤其想讲清楚：一个模块拿到什么输入、交出什么结果，和其他模块怎么配合。

内容够用、有人愿意持续维护后，再增加正式导航和准备路线。不会先挂一排空栏目，也不要求新贡献者认领整个方向。涉及真机或车辆的例子，要另讲实验条件、失效情况和安全边界，不能把「在仿真里跑通」当成「可以放心上实物」。

## 想参与，从哪儿下手？ {#contribute}

改错字、补一张图、解释一个难点，都可以直接提小 PR。还没想好怎么改，也可以先[提反馈](https://github.com/tianyi-zhang-02/cooking-agi/issues/new?template=note-feedback.yml)。不需要先成为某个领域的专家。

想加新方向，先开[内容提案](https://github.com/tianyi-zhang-02/cooking-agi/issues/new?template=proposal.yml)，写清四件事就够了：

1. **给谁看**：完全入门、已有基础，还是在准备某类技术面试？
2. **先解决哪一个问题**：不用一上来就写完整系列。
3. **拿什么讲清楚**：公开来源，一个小例子，或者能复现的实验。
4. **愿意做到哪一步**：提纲、正文、代码、翻译或审核；有多少时间就做多少。

维护者会先确认范围和放在哪里，再找愿意参与的审核人。你可以只贡献一次，不代表接下了长期维护。普通修改走 [PR 审核流程](README.md#review)，跨板块的大改先讨论。

一篇能交付的笔记，应有前置知识、从小例子到原理的讲解、练习或验证方法，以及适用条件和局限。涉及设备时写清成本与版本；能给 CPU 或仿真替代就给，给不了也直说。英文和中文分别写顺，不是逐词翻译。引用保留来源，没跑过的实验不写成实测。

## 网站怎样更新？ {#versions}

网站不打版本号。改动合并进主分支、部署成功后就上线；每天还会定时重建几次，更新贡献者名单这类数据。每次合并改了什么，按日期记在首页的[更新记录](../README.zh.md#changelog)里；某篇文章的具体修改，可以看页尾的源文件和仓库历史。

收藏和阅读记录的备份格式单独管理，网站更新不会让旧备份失效。浏览器数据也不是永久备份：清理网站数据、换设备或换域名之前，请先导出。

新方向可以通过提案调整，不要求按这张表的先后顺序来。网站会一直免费；如果它帮到了你，欢迎分享给同样需要的朋友。
