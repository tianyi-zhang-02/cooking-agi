# 下一站：投稿与展示说明

**中文** · [English](next-stop-guide.en.md) · [回到下一站](next-stop.md)

学完以后去了哪里，也值得记一下。这里欢迎你分享实习、全职或转行的近况，但不收集录取证明，也不把大家的经历变成网站的业绩。

## 我想分享，怎么做？

1. 打开[投稿表单](https://github.com/tianyi-zhang-02/cooking-agi/issues/new?template=next-stop.yml)，填公司、岗位类别、工作类型和**开始时间**，例如 May 2026 或 2026-05。尚未入职的填预计开始时间；月份不确定或不想公开，只填年份就好。再选拿到 offer、已入职或已结束，也可以补充具体岗位名，例如 ML Engineer Intern。
2. 想让大家认出你，就勾选展示 GitHub 用户名。页面会在这条经历旁显示可点击的 `@用户名`，连到你的 GitHub 主页；星空里的详情也能看到。不想公开账号也可以只用昵称，或不署名。愿意的话，留一句哪些笔记帮到了你，或哪些地方还缺内容；不用写推荐语。
3. 维护者确认你同意展示哪些字段、是否已有同一段经历，再通过 PR 加入。未经同意，不从社交主页、GitHub 或聊天记录中收集经历。

**GitHub issue 是公开的。** 网页不署名不等于完全匿名：issue、提交历史仍可能关联你的账号。如果不希望这些信息公开，请不要通过这个表单提交。

别上传 offer 文件、薪资、证件、联系方式或招聘私信。只分享自己的经历，不替同事、同学或朋友投稿。

## 页面上的数量是什么意思？

- 时间线按**开始年月**由近到远排列，不按收到 offer、结束或投稿的时间排序。尚未入职的会标注「预计」。只有年份的记录放在该年末尾，不推断月份，也不表示发生在 12 月。
- 公司汇总统计当前筛选下的**公开记录条数**，并列按公司名排序。它不是公司质量榜，也不是独立人数、录取率或使用网站后的成功率。
- 一个人可以有不同经历，但同一份 offer 后来入职、再结束，应更新原记录，而不是每个阶段再计一次。实际开始时间确认后可以修正；结束一段经历只改状态，不把开始时间换成结束时间。
- 岗位大类用于筛选：SWE / SDE 归软件工程，MLE 归机器学习工程，RS / RE 归研究；数据、产品、其他单独分组。拿不准就由投稿者确认，不根据公司名猜岗位。
- 内容为 **self-reported**。维护者检查同意范围、格式和重复项，不代表替公司核实了录用结果，更不能说明网站导致了这次录用。

## 公司不在列表里怎么办？

照常分享就好，图标库不是公司白名单。我们预设了一批 Tech、AI、软件和量化公司的标识；暂缺 logo 的直接用完整公司名，不截成单个字母，也不会影响你的去向展示。

想补一个？打开[公司图标申请](https://github.com/tianyi-zhang-02/cooking-agi/issues/new?template=company-icon.yml)，带上**公司名、官网、公开的 logo 或品牌资源链接**。简称和中文名也可以一起写，方便搜索。表单会把 issue 指派给 **@tianyi-zhang-02**，你也可以在补充说明里 ping 我一下 :) 我确认资源后会加入。

不收内部文件，不自动下载投稿链接，也不会自动上线。图标只是为了方便认出公司，不代表有人入职、公司合作或认可这个站点。

## 修改、撤下与隐私

通过同一表单选择「修改」或「撤下」，写记录编号即可，不必重复公开原经历。维护者确认请求来自本人后更新页面。

已经公开的 issue、Git 历史、分叉和外部缓存可能保留旧内容，撤下网页不能保证抹去这些副本。因此我们一开始就尽量少收集信息。

## 维护者怎么加记录？

源数据放在 `community/outcomes.json`，网页由 `site/next_stop.py` 构建，中英文共用一份数据。没有已获同意的投稿时就留空，不使用虚构案例充数。

每次更新走一个小 PR：

1. 检查本人投稿、明确展示同意和已有重复记录。统一公司 ID；同一公司不要因大小写或别称拆成两家。
2. 新记录使用不变的 `NS-0001` 形式编号。`start_date` 保存开始年月，只接受 `YYYY` 或 `YYYY-MM`；表单中的 May 2026 应整理为 `2026-05`。不能用收到 offer 或投稿的时间代替，拿不准就请本人确认。`source_issue` 记录同意来源，`consent` 必须为 `true`。它们用于追溯，不在页面直接链接投稿人的 issue。站点作者亲自要求加入自己的经历时，可用 `owner_submission: true` 代替 `source_issue`，但 `github` 必须是站点配置中的作者账号；不能替别人使用，也不能编造 issue 编号。
3. 必填字段为 `id`、`start_date`、`company`、`role`、`employment`、`milestone`、`consent`，以及上述一种同意来源。`company` 引用 `companies` 字典中的 ID；字典值是公开展示的公司名。
4. `role`：`software / ml / research / data / product / other`；`employment`：`internship / full-time / contract / other`；`milestone`：`offer / started / completed`。可选 `title` 提供 `zh`、`en` 两个版本的具体岗位名，每种不超过 100 字符；不填则显示岗位类别和工作类型。转行可以在可选留言里说明，不替代工作类型。
5. `name` 和 `github` 只在分别同意展示时加入；不填则显示「一位读者」。有 `github` 时明确展示 `@用户名`；若也填了昵称，两者一起显示，不用昵称替代账号。可选 `note` 同时提供 `zh`、`en`，每种不超过 400 字符，翻译不要补出原文没有的结果。公开仓库中的源数据同样是公开的，不能往里面放私有审核备注。
6. 按现有协作规则审阅，运行下面的检查再合并。审核者不足时如实记录，不把自动检查写成独立审核。

公司预设单独放在 `site/company-icons.json`，SVG 放在 `site/static/company-icons/`。新增时复用已有 ID，补上别名和公开来源；只收静态 SVG，先检查没有脚本、外链或嵌入内容。没有合适 logo 就直接显示完整公司名，不用为了凑齐临摹一个。**新增图标不新增去向记录**，公司图标申请和本人经历投稿是两回事。

```sh
python3 -m unittest discover -s site/tests
python3 site/paritycheck.py --strict
python3 site/leakcheck.py
python3 site/build.py
```

维护流程沿用[社区协作规则](README.md)，不另设一个委员会，也不按公司的名气决定是否展示。
