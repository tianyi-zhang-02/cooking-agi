# 扩散解码的缓存：哪些能复用，哪些还得重算

**中文** · [English](context-reuse.en.md)

> 阅读时间：约 10 分钟 · 最近审阅：2026-10

一篇长文已经读过了，为什么扩散语言模型生成下一小块文字时，还要一轮轮访问它？[分块扩散](ar-and-diffusion.md#block-cache)能保留已完成前缀的 KV，但“这些表示不用重算”和“以后不用再读这些表示”是两件事。

这一篇沿着数据流看缓存：先把精确复用的条件讲清，再看 E2D2、FlashBlock 和 MAGE 分别省了哪一部分。它们不是三个互相替代的开关，也不能只按论文里的加速倍数排序。

## KV 固定，attention 的结果也会固定吗？

不会。当前块里的词在变化，query（查询向量）也可能跟着变。它与历史 key（键向量）匹配，决定各位置的权重，再对 value 中的信息加权求和。即使历史的 key 和 value 完全没变，读出来的结果仍可能不同：

$$
A(q)=\operatorname{softmax}\left(\frac{qK^\top}{\sqrt d}\right)V.
$$

用一个一维例子。历史只有两个位置，$K=[0,1]$，$V=[0,10]$，$d=1$。记 $Z$ 为 softmax 分母，也就是两个分数取指数后的和。

| 当前 query | 指数权重 | $Z$ | 历史 attention 输出 |
| --- | --- | --- | --- |
| $q=0$ | $[1,1]$ | 2 | 5 |
| $q=\log3$ | $[1,3]$ | 4 | 7.5 |

历史一个字都没动，但 query 改了，输出从 5 变成了 7.5。因此，复用这段历史的 **KV** 可以是精确的；直接复用上一步的 **attention 输出**，还需要额外条件。一般情况下，后者是近似。

```text
已完成前缀 → 保存的 K、V ─────┐
                            ├→ attention → 当前层输出
当前块 → 本轮 query ─────────┘
          ↑
     下一轮可能改变
```

这里的“KV 可精确复用”仍有前提：前缀被块因果注意力隔离，不受当前块更新影响。普通整段双向模型不能直接套用，见[前缀缓存例子](ar-and-diffusion.md)。

## 三种方法，改的不是同一处

| 方法与版本 | 复用什么 | 仍要做什么 |
| --- | --- | --- |
| [E2D2，NeurIPS 2025](https://proceedings.neurips.cc/paper_files/paper/2025/file/172e31282df16359324717fcfbdbead3-Paper-Conference.pdf) | encoder 为干净上下文算出的特征或 KV | 较小的 decoder 多轮去噪；块完成后，encoder 处理新块 |
| [FlashBlock，2026-07 v3](https://arxiv.org/html/2602.05305v3) | 块外 attention 输出及其归一化统计量 | 重算块内 attention，合并两部分，并按策略刷新缓存 |
| [MAGE，2026-06 v2](https://arxiv.org/html/2602.14209v2) | 当前块首次全 `[MASK]` 时选出的历史 KV 索引 | 后续轮次用新 query，对选中的 KV 重新计算 attention |

E2D2 的分块版本把重的上下文编码和反复执行的去噪分开。它提供最终隐藏状态、逐层共享 KV 两种连接方式，不等于“把整段历史压成一个向量”。这是配套训练的架构，不能把普通 checkpoint 随手拆成两半就得到同样效果。[原文 §3.2–3.3](https://proceedings.neurips.cc/paper_files/paper/2025/file/172e31282df16359324717fcfbdbead3-Paper-Conference.pdf)

FlashBlock 依赖块外 attention 跨步较稳定的观察，不保证每次都不变。v3 还提供可选的 LoRA 蒸馏来适应复用误差；不能把所有结果都称为“完全不训练的加速”。[原文 §4](https://arxiv.org/html/2602.05305v3#S4)

MAGE 缓存的是**去哪里读的索引**，不是读出来的答案。索引按层、KV head 选择，再在该块后续步骤中复用，并不是所有层共享一份清单。它减少历史 KV 的访问量，但仍保留完整 KV cache，不因此减少整份缓存的显存占用。[原文 §4、§6](https://arxiv.org/html/2602.14209v2#S4)

另一个容易混淆的名字是 [Block Transformer](ar-and-diffusion.md#hybrids)：它也做全局与局部的分工，但局部生成仍是自回归，不能因为有“分层”和“块”就归为扩散模型。

## 为什么合并两个 attention 不能直接取平均

把 key 分成历史部分和当前块。各自算出的输出已经在各自范围内做过 softmax，两个范围拿到的总权重不一定相同。

对同一个 query、同一层同一个 head，设两部分输出为 $A_{\mathrm{hist}}$、$A_{\mathrm{block}}$，对应 softmax 分母为 $Z_{\mathrm{hist}}$、$Z_{\mathrm{block}}$。正确的合并是：

$$
A=\frac{Z_{\mathrm{hist}}A_{\mathrm{hist}}+Z_{\mathrm{block}}A_{\mathrm{block}}}
{Z_{\mathrm{hist}}+Z_{\mathrm{block}}}.
$$

沿用前面的新 query：历史输出为 7.5，分母为 4。再假设当前块有一个 key，分数为 0、value 为 2，因此当前块输出为 2、分母为 1。完整输出为：

$$
A=\frac{4\times7.5+1\times2}{4+1}=6.4.
$$

直接平均会得到 $(7.5+2)/2=4.75$，不对。若连历史输出和分母都沿用旧值，则得到 $(2\times5+1\times2)/3=4$，同样不是这一轮完整计算的结果。

所以，只缓存一个 attention 输出向量还不够，合并时需要它的归一化统计量。实现中通常保存 $L=\log Z$，用减最大值的方式稳定计算：

$$
\begin{aligned}
m&=\max(L_{\mathrm{hist}},L_{\mathrm{block}}),\\
A&=\frac{e^{L_{\mathrm{hist}}-m}A_{\mathrm{hist}}+e^{L_{\mathrm{block}}-m}A_{\mathrm{block}}}
{e^{L_{\mathrm{hist}}-m}+e^{L_{\mathrm{block}}-m}}.
\end{aligned}
$$

这个合并公式在两部分统计量都来自**当前 query** 时是精确的。若历史部分来自旧 query，公式算得再准确，也没有消除缓存过时造成的误差。这正是 attention 输出复用需要验证的地方。[FlashBlock 的分解公式](https://arxiv.org/html/2602.05305v3#S4.SS2)

## 省了历史访问，不代表整段生成同样变快

假设原本生成一块要 100 ms：60 ms 花在读取历史并计算 attention，另外 40 ms 花在投影、FFN、采样等操作上。把前者加速三倍，整块耗时变成：

$$
T_{\mathrm{new}}=60/3+40=60\text{ ms},\qquad
S=100/60\approx1.67.
$$

如果索引选择、刷新和合并还额外花了 8 ms，总时间就是 68 ms，加速约 $1.47\times$。这是不考虑操作重叠的教学算例，不是任何论文的实测。

短上下文可能本来就没多少历史可读；去噪只跑几轮时，首次选择索引的成本也更难摊薄。比较实现时要记录完整块耗时，而不是只测省下来的那个 kernel。峰值显存另记，访问变少不自动等于占用变少。

## 如果想验证一个复用方案，先拆开看误差

假设模型要从一份长合同中提取金额，并在后文说明罚款条件。只看平均分可能发现不了：金额还对，但生成到罚款条款时应该读取另一段历史，旧的 attention 输出或索引没跟上。

可以先做下面这组诊断。这是实验设计，不是已经完成的测量，也不把“缓存加一个修正器”当作已验证的新方法。

| 对照 | 能区分什么 |
| --- | --- |
| 固定输入状态，每轮完整 attention | 得到逐层参照，不混入采样轨迹的差异 |
| 只缓存精确的已完成前缀 KV | 先确认基础缓存实现没有改结果 |
| 冻结历史输出与归一化量，改变刷新间隔 | 量出旧 query 带来的误差及刷新成本 |
| 冻结历史索引，仍用新 query 计算 | 区分“选错历史”和“沿用旧输出” |
| 恢复自由生成，保持相同解码预算 | 观察局部误差是否改变后续选择和任务结果 |

逐层可以比较输出误差，最终还要看 token 分布、答案质量和延迟。相同随机种子不保证两个实现始终走同一条生成轨迹，因此固定状态的对照和自由生成的评估都需要。

若还想把历史压缩成更短的表示，要再单独检查细节是否丢失：原文里的金额、日期、否定词能否找回来？更小的表示、更少的读取、较少的刷新是不同选择，不能因为都叫“复用上下文”就一起算成一个优化。
