# Agents：用 frontier API 还是自己 serve

**中文** · [English](model-choice.en.md)

> 阅读时间：约 6 分钟 · 难度：进阶 · 最近审阅：2026-09

## 先看能力够不够

agent 的错误会沿着步骤累积。如果每一步独立地有 95% 的概率做对，20 步全对的概率只有

$$0.95^{20} \approx 0.36$$

单步差那么一点，放到长任务里就被放得很大。所以先在**自己的任务**上测一遍：开源模型够不够用？不够，后面那些因素都不用谈。

## 几个维度一起看

| 维度 | Frontier API | 自己 serve（开源权重） |
| --- | --- | --- |
| 能力上限 | 通常更高，长任务和复杂规划尤其明显 | 看选哪个模型，窄任务上往往够用 |
| 成本结构 | 按 token 付费，量小的时候便宜 | GPU 和人力是固定开销，量大又稳定才划算 |
| 延迟 | 看网络和服务商当时的负载 | batch 和部署位置都能自己调 |
| 数据与合规 | 数据得发给服务商 | 数据不出自己的环境 |
| 定制 | 主要靠 prompt，有些支持微调 | 可以拿自己的数据微调、做 RL |
| 版本控制 | 什么时候更新、什么时候下线，服务商说了算 | 自己决定什么时候换 |
| 运维负担 | 几乎没有 | 推理框架、扩缩容、监控全得自己扛 |

## 成本怎么算

agent 很吃 token：一个任务动辄几次到几十次模型调用，而且每一步都要把越来越长的上下文重发一遍。下面这张图可以填自己的数字：API 的成本随 token 数线性增长；自己 serve 则有一块固定成本（全天开着的 GPU，加上维护它的人），流量超过一组副本的容量，才会往上跳一级。

## 不是二选一：混着用

大多数系统最后都不会只用一种模型，而是把同一批流量分给两个模型。下面比较四种分法：

<!-- widget:tx-model-router -->

- **级联**：小模型先答，拿不准的再升级给 frontier。FrugalGPT（2023）研究的就是这个。
  代价是被升级的请求要付两次钱。
- **路由**：先判断难度，再决定派给谁，一条请求只付一次。RouteLLM（2024）训练的就是这样的路由器。
  但它要在看到答案之前做决定，猜错了也没有补救。
- **蒸馏**：在请求量大、任务固定的场景里，先用 frontier 模型生成示范轨迹，再用它们微调一个自己 serve 得起的小模型。
- **兜底**：自己的模型处理常见情况，异常再交给 frontier。

上面那张图里，关键是「难度判断准不准」。判断准，级联和路由都很划算；判断接近随机猜，
这两种方案还不如只用一个模型，多出来的那一层只会增加出错的地方。

## 成本之外的三件事

**延迟会叠加。** agent 一个任务要调好几次模型，用户感受到的是这几次之和。
首 token 时间（TTFT）和每 token 时间要分开看：短回答受 TTFT 主导，长回答受后者主导。
自己 serve 可以调整 batch、显卡型号和部署位置；用 API 就只能等服务商。

**上下文往往是最大的开销。** agent 每一步都要把越来越长的历史重新发一遍；如果每步新增的内容差不多长，
总 token 数大约随步数的平方增长。prompt caching（把不变的前缀缓存起来）在这里最省钱；选服务商时，
值得问清楚能不能缓存、能缓存多久。

**模型会变。** API 背后的模型会更新、会下线，同一个 prompt 几个月后可能得到不同的回答。
自己 serve 的权重不会自己变，代价是安全更新也要自己跟进。两种情况都需要回归测试，
及时发现「上周还好好的，这周坏了」这类问题。

## 自己 serve 的成本到底由什么决定

成本不只是买几张卡，关键在利用率：

- **并发与批处理**：一张卡同时处理的请求越多，摊到每条上的成本越低。流量有波峰波谷，
  按峰值买卡、平时只用到平均水平，中间那部分就是闲置的成本。
- **KV cache 占显存**：对长上下文的 agent 来说尤其明显，显存会比算力先成为瓶颈，能同时处理的请求就变少了。
  vLLM 的 PagedAttention 和 SGLang 的 RadixAttention 都是为了解决这个问题。
- **人**：推理框架升级、扩缩容、监控、值班。这一项在小团队里往往比 GPU 还贵。

## 一个决策顺序

1. 数据能不能离开自己的环境？不能，就只能自己部署。
2. 在自己的评估集上，开源模型达不达标？不达标，就用 frontier 模型。
3. 流量是不是又大又稳定？是，自己 serve 的成本优势才会出现。
4. 需不需要在自己的数据上微调或做 RL？需要，就更倾向开源权重。
5. 都还说不准，就先用 API 上线，把质量和成本测出来，再回头算这笔账。
