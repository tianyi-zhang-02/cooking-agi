# Agents：用 frontier API 还是自己 serve

**中文** · [English](model-choice.en.md)

> 阅读时间：约 2 分钟 · 难度：进阶 · 最近审阅：2026-09

## 先看能力够不够

agent 的错误会沿着步骤累积。如果每一步独立地有 95% 的概率做对，20 步全对的概率只有

$$0.95^{20} \approx 0.36$$

所以单步能力上一点点差距，放到长任务里会被放大很多。先在**自己的任务**上评估：开源模型能不能达到要求？达不到，其他因素都不用谈。

## 几个维度一起看

| 维度 | Frontier API | 自己 serve（开源权重） |
| --- | --- | --- |
| 能力上限 | 通常更高，尤其是长任务和复杂规划 | 取决于选的模型，窄任务上可能够用 |
| 成本结构 | 按 token 付费，量小时便宜 | 固定的 GPU 和人力成本，量大且稳定时更划算 |
| 延迟 | 受网络和服务商负载影响 | 可以按需求调 batch、部署位置 |
| 数据与合规 | 数据要发给服务商 | 数据不出自己的环境 |
| 定制 | 主要靠 prompt，部分支持微调 | 可以在自己的数据上微调、做 RL |
| 版本控制 | 服务商决定模型什么时候更新或下线 | 自己决定什么时候换 |
| 运维负担 | 几乎没有 | 推理框架、扩缩容、监控都要自己做 |

## 成本怎么算

agent 会把 token 用量放大：一个任务往往要几次到几十次模型调用，而且每一步都要把越来越长的上下文重新发一遍。下面这个模型可以填自己的数字：API 的成本随 token 线性增长；自己 serve 有一块固定的底（全天运行的 GPU 加上维护它的人），超过一组副本的容量才往上跳。

## 常见的折中：混着用

- **路由与级联**：简单的步骤交给小模型，难的交给 frontier 模型。FrugalGPT（2023）研究了按顺序调用、够好就停的级联；RouteLLM（2024）训练了一个路由器，在强弱两个模型之间分配请求。
- **蒸馏**：用 frontier 模型在某个量大且固定的窄任务上产生轨迹，再微调一个自己能 serve 的小模型。
- **兜底**：自己的模型处理常见情况，遇到把握不大的再交给 frontier 模型。

自己 serve 时，vLLM（PagedAttention）和 SGLang 是常用的推理框架。

## 一个决策顺序

1. 数据能不能离开自己的环境？不能，就只能自己部署。
2. 在自己的评估集上，开源模型达不达标？不达标，就用 frontier 模型。
3. 流量是不是又大又稳定？是，自己 serve 的成本优势才会出现。
4. 需不需要在自己的数据上微调或做 RL？需要，就更倾向开源权重。
5. 都不确定，就先用 API 上线，把评估和成本都测出来，再回头看。
