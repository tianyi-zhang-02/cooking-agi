# Agents：几种常见结构

**中文** · [English](patterns.en.md)

> 阅读时间：约 2 分钟 · 难度：进阶 · 最近审阅：2026-09

## 最小单位：增强过的模型

所有结构的起点都是一个接上了检索、工具和记忆的模型（Anthropic 叫它 augmented LLM）。下面几种 workflow 和 agent，都是把这个单位用不同的方式组合起来。

## 五种 workflow 和一种 agent

| 结构 | 怎么做 | 什么时候用 |
| --- | --- | --- |
| Prompt chaining | 把任务拆成固定的几步，上一步的输出是下一步的输入，中间可以加检查 | 步骤清楚，愿意用一点延迟换准确 |
| Routing | 先分类，再交给专门的处理路径 | 输入类型差别大，分开处理更好 |
| Parallelization | 拆成独立的子任务同时做（sectioning），或同一件事做几遍再投票（voting） | 子任务互不依赖，或想要更稳的结果 |
| Orchestrator-workers | 一个模型动态拆任务、分给 worker、再汇总 | 子任务事先列不出来，比如要改哪些文件取决于需求 |
| Evaluator-optimizer | 一个模型生成，另一个评价并给反馈，循环改进 | 有清楚的评价标准，而且反馈确实能让结果变好 |
| Agent | 模型在循环里自己决定每一步，靠环境反馈判断进展，直到满足停止条件 | 开放式任务，步数和路径都预先不知道 |

从上往下，灵活性越来越高，可预测性、成本和调试难度也越来越高。

## 怎么选

- 先用单次调用加好的 prompt 和检索试一试，很多问题到这里就够了；
- 能写成 workflow 就写成 workflow：每一步可以单独测、单独改；
- 只有当路径真的无法事先确定时，才换成 agent，并且给它清楚的停止条件和预算。

## 框架还是直接调 API

很多框架能让你几行代码搭出 agent，但也会把 prompt 和模型的真实输入输出藏起来，出了问题难查。Anthropic 的建议是先直接调模型 API，很多模式几行代码就能实现；用框架时，要确认自己理解它底下在做什么。
