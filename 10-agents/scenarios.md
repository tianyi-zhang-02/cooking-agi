# Agents：不同场景怎么用

**中文** · [English](scenarios.en.md)

> 阅读时间：约 4 分钟 · 最近审阅：2026-10

## 最关键的区别：能不能自动验证

同样叫 agent，写代码和订机票差别很大。最关键的区别是：**做完之后能不能自动判断对不对**。能自动验证的场景，可以让 agent 在沙箱里多试几次，测试通过后仍要人看 diff；不能验证的场景，每一步都更需要人来把关。

| 场景 | 环境与工具 | 能不能自动验证 | 最常见的失败 | 护栏 |
| --- | --- | --- | --- | --- |
| 写代码 | 代码仓库、shell、测试 | 能：跑测试 | 测试过了但逻辑是错的；为了过测试去改测试 | 沙箱执行；人看 diff |
| 搜索与研究 | 搜索、网页读取 | 部分：能核对来源 | 编造引用；不知道什么时候该停 | 要求给出处；设预算 |
| 客服 | 订单与用户系统、政策文档 | 部分：规则能查 | 违反政策；同一问题几次回答不一样 | 限制工具权限；复杂情况转人工 |
| 数据分析 | SQL、notebook | 部分：查询能跑，结果对不对还要核对 | join 或过滤条件写错，结果看起来却很合理 | 展示实际执行的查询；核对行数和统计口径 |
| 操作电脑和浏览器 | 网页、图形界面 | 弱 | 界面一改就失效；网页里隐藏的内容可能被当成指令 | 不可逆的操作要确认；运行环境要隔离 |
| 个人助理 | 邮件、日历、记忆 | 弱 | 按过时的记忆行事；泄露隐私 | 发送前先确认；记忆可以被纠正 |

### 算一下：能验证，多试几次才有用 {#retry-math}

假设 agent 每次尝试互相独立，做对的概率都是 $p=0.9$，一共跑 $k$ 次。

- **能自动验证**（写代码、跑测试）：跑 $k$ 次，留下第一份通过验证的结果。只要有一次做对就行，成功率是 $1-(1-p)^k$，常记作 pass@k。
- **不能自动验证**（客服直接回复用户）：每次运行用户都会看到，$k$ 次都得做对，概率是 $p^k$，也就是 [τ-bench](https://arxiv.org/abs/2406.12045) 用的 pass^k。

| 运行次数 $k$ | 能验证：$1-(1-p)^k$ | 不能验证：$p^k$ |
| --- | --- | --- |
| 1 | 0.900 | 0.900 |
| 3 | 0.999 | 0.729 |
| 8 | ≈1.000 | 0.430 |

同一个 agent、同样 90% 的单次成功率，多跑几次，在左边几乎一定能拿到一份对的；在右边，全部做对却越来越难。所以能验证的场景可以放手让 agent 多试；不能验证的场景，要先把单次可靠性做上去，再配上权限限制和人工确认。

左边这一列靠两个前提，现实里常常不成立：

- **验证得可靠。** 测试漏掉的错误代码也会被当成“通过”留下来，挑出来的那份不一定对。
- **每次尝试得独立。** 如果失败集中在同一类难题上，换个随机种子再跑 8 次，可能 8 次都错在同一处。

## 写代码：验证信号最强的场景

代码能运行、测试能判断对错，这是 agent 最理想的环境：每一步都有客观反馈。SWE-bench 就是用真实的 GitHub issue 和配套测试来评估这类 agent 的。它最常被引用的 Verified 子集已经接近做满，题目也可能被模型见过：OpenAI 在 2026-02-23 的说明里表示不再报告 SWE-bench Verified，改为推荐题目更难、仓库更多的 [SWE-bench Pro](https://arxiv.org/abs/2509.16941)（[OpenAI 的说明](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)）。基准为什么会被做满、被污染，见[测试时计算：怎么读数字](../11-frontier/test-time-compute/measuring.md)。但测试通过不等于改对了，测试没覆盖到的地方，还是需要人来检查。

## 客服：可靠性比单次成功率重要

同一个问题，这次答对、下次答错，在客服场景里是不能接受的。τ-bench 模拟用户和受政策约束的工具环境，用 pass^k 衡量可靠性：同一个任务独立跑 k 次、k 次全部成功的概率，再对任务取平均。它比只看一次成功率更接近真实要求：单次成功率 90% 的任务，8 次全对的概率只有 $0.9^8\approx0.43$（见[上面的表](#retry-math)）。它的后续版本 [τ²-bench](https://arxiv.org/abs/2506.07982) 加了电信客服场景：用户也要自己动手操作设备（dual control），agent 得指导用户一起完成。截至 2026-10-21，[仓库](https://github.com/sierra-research/tau2-bench)的[最新发布](https://github.com/sierra-research/tau2-bench/releases)是 2026-10 的 τ-bench 2.0，加入了同一批客服任务的六种语言版本。在它之前，τ³-bench（v1.0）加入了语音全双工评估和 banking_knowledge 领域；2026-07 的 v1.0.1 修正了这个领域的评分，仓库说明这个领域在 1.0.1 之前和之后的结果不能直接比较。

## 读外部内容的 agent：小心注入

只要 agent 会读取网页、邮件、文档这类不受你控制的内容，就可能被其中隐藏的指令劫持（indirect prompt injection，[Greshake 等，2023](https://arxiv.org/abs/2302.12173)）。要守住两条底线：外部内容只当数据，不当指令执行；有副作用的操作要限制权限，并且要经过人确认。

## 怎么评估

- 代码：SWE-bench；也可以看 SWE-bench Pro，上文链接的 OpenAI 2026 年 2 月说明推荐了它；
- 网页任务：WebArena；
- 操作电脑：OSWorld；
- 带政策约束的对话与工具：τ-bench 及后续的 τ²-bench、τ³-bench 和 τ-bench 2.0。

公开 benchmark 只是起点。上线前，要在自己的任务上建立评估集，并检查完整的运行轨迹，见 [Agent Observability](../06-systems/agent-observability.md) 和 [Evaluation](../07-evaluation/)。
